# 邮件 AI 自审、有限重试与失败告警

2026-10-12 用户明确授权免人工点击发送，并将自审范围收窄为文案与图片 Visual Handoff。工作日 08:30 的现有定时任务进入 `run_ai_daily.py publish-reviewed`：生成正文与图片 → 构建 HTML → 文案审核与成图对照 Handoff 检查 → 打包并发送至现有正式名单。审核通过即发送，不再等待人工确认；不用另启 09:20 的旧发布定时器。

## 审查与恢复

- 检查当前内容校验、输入文件一致性、日期、栏目与 HTML 构建签名；AI 阅读实际最终 HTML 提取的正文、标题和链接，只用邮件已采用条目对应的资料核对事实，不重新判断选题价值。审核输入不含候选池、落选理由、评分与来源等级。
- 预览中的评分/留言占位链接不提交模型判断；这些控件在打包时个性化，SMTP 前逐封检查实际 EML，残留占位链接会阻断发送。
- 有研究图时，文案审核同时检查六项 Visual Handoff 的一致性，视觉模型只对照交接检查实际图片的关键文字、主机制、数字名称和能力边界。自动发布把真实结果保存为明确标识的 AI 图片审批记录，并绑定原图、交接材料和实际邮件图的指纹；不填写或伪造人工检查结果。
- 候选覆盖复核已退出自动发布和手动正式发送入口，`selection_policy.json` 的 `coverage_review.enabled=false`。选源与评分仍用于上游生成日报，但发送前不重审候选、入选资格、论文回看范围或落选理由；旧覆盖复核脚本与记录仅供按需诊断。
- 用户明确保留四类修复：事实错误、图片错误、已选内容丢失和时间冲突。程序只比对已选条目是否出现在成稿；已刊条目的日期冲突作为事实资料交给文案审核，明确说明回顾或日期边界可通过，不因时间字段有差异直接退稿。成功生成前的接口重试记录本身不构成文案错误。
- 2026-10-13 按用户反馈降低非必要退稿：只有高置信、足以误导核心理解的明确错误进入 `issues`。缺少非关键日期、套餐细则或可改进的链接文字，放入 `advisories`，不令审核失败、不重试、不发告警；不能仅凭当日期号推断每条新闻都声称当天发生。实际写错主体、因果、数字、适用范围或事件时间，仍需修正。每个阻断项须引用原句、事实依据并说明实质影响。
- 总计最多 **3 轮**，即首次执行加 **2 次重试**，分别等待 30 秒、60 秒。重试不会换用更弱的审查模型或跳过门禁。生成器原有的局部请求重试与正文修复仍保留，因此 3 轮不是 3 次模型调用。
- 文案审核失败时，模型给出精确字段的 `before/after` 修补，程序只改对应文字并用原图重建邮件。来源 URL、图片、选题、顺序、生成元数据及其他条目不在可写范围。补丁过期、越界或构建失败时保留原稿，把诊断交给下一轮审核，不退回整篇重写。修补历史保存到 `copy_repair_history.json`。
- 图片实质错误只重生成图片并复审，文案保持不变。QA 接口暂时不可用或返回非法 JSON 时只重试审查。只有尚未形成可审稿件的生成/结构问题才走原有生成恢复。已部分正式投递的日报禁止重新生成，避免同一期内容混用。
- 图片审批仅补充审核元数据时，逐项确认正文、图像、交接和来源指纹未变化，再刷新审批清单绑定；不为同一成品重复调用一次正文和图审。任何成品变化仍需复审。
- 每轮开始就写入预算，进程重启不会获得额外次数；耗尽后不会因再次调用而继续生成。修复根因后，使用 `--rebuild` 显式开启新一轮。
- 成功审查记录绑定正文、规范化输入、HTML、来源材料、选源、图片、图片清单、研究交接和审查代码版本。任何变化都需要复审；SMTP 前再次核对指纹。

## 告警

告警只发给一个编辑邮箱：优先使用环境变量 `AI_DAILY_ALERT_TO`，否则读取本机 `config/editor_settings.json` 的 `footer.email`。它不读取正式收件名单，不把告警群发。

内容包括期次、失败阶段、各轮报错、按错误类别给出的建议与日志位置。使用固定纯文本模板，即使 AI 服务停机也可生成；建议明确标为待核实，报错先脱敏。SMTP 失败保留 EML 和失败记录；发送结果不确定时不盲目重发。每期每个阶段成功告警后不重复通知。

SMTP 投递失败另发一次编辑告警，但不自动整期重发。已有投递明细应先核实，再通过原发送包续发。
自动发布在打包/投递前先写 `automatic_delivery_state.json`；即使进程在第一位收件者确认前中断，重启也会阻断自动重发并告警，避免结果不明时重复投递。

## 配置与记录

### 2026-10-14 证据与 trace 修补

- 生成与发送审核共用 `editorial_evidence.py`，区分抓取正文、上游编辑摘要与发现摘要。已选事件的其他来源引文经过原始选源材料指纹和逐字匹配检查后，连同 URL、原文指纹传入 `supporting_evidence`；不带入候选排名或落选材料。历史材料缺少该字段时，审核只从同一已选事件、相同评估输入指纹恢复引文。主正文未提及不等于否定；摘要本身也不被提升为已核实事实。
- 每次实际审核生成唯一 `review_id`，在 `email_review_history/<review_id>/` 保留输入、开始、文案返回、图审返回和最终结果。图审输入包含实际送审图像，目录和文件按私有权限保存。`email_self_review.json` 仍为最新兼容入口，包含历史路径和恢复轮次；命中完全一致的成功缓存不产生新审核。
- 首轮失败、异常中断、旧版收据与修补诊断不会被后续审核覆盖。图片批准后的元数据绑定另存审批事件，原始审核结果保留。记录能保存已返回的 request ID 和用量；服务未返回的调用信息不会伪造。
- 候选图构建只记录候选状态；AI 图片批准后才写审批事件并同步最新 manifest、审核收据与 HTML 指纹。每个工作流事件保留当时的资产描述。比较版 HTML 以内容指纹命名、保存在同一输出目录，后续文案修补不会覆盖其内容。

本次修复不改变三轮恢复预算、发送名单、工作日历和防重复投递规则。更新系统服务时使用仓库中的 `deploy/systemd/ai-daily-prepare.service`，并只执行 daemon-reload；安装本身不启动或补发日报。

策略文件为 `config/email_quality_policy.json`，保存审核范围 `review_scope=final_copy_and_visual_handoff`、重试参数和告警邮箱的配置来源，不保存凭据。

`ai_review_enabled` 是实际联网审查开关。`automatic_send_enabled` 是自动正式发送开关，配合 `automatic_send_authorization` 记录用户授权；两项均已按本次用户授权启用。自动发送入口要求两个开关都为 true，任一关闭都不能自动发信。

每期 `daily_runs/YYYY-MM-DD/` 保存：

- `email_self_review.json`：审核范围、文案与成图结果、已选内容完整性与时间冲突记录、模型信息、资产指纹。
- `prepare_recovery.json` / `prod_recovery.json` / `publish_recovery.json`：持久化轮次、阶段、错误、最终状态及告警状态。自动发布的生成及全部审核共享 publish 的 3 轮预算。
- `research_image.automated_editorial_review.json`：AI 图片审批依据。已有的 `high_value_coverage_review.json` 留作历史诊断，不再是发送条件。
- `quality_attempt_logs/`：生成/构建子进程日志，单阶段最多运行 30 分钟。
- `*_failure_alert.eml` / `*_failure_alert.json`：告警原件及投递结果；这些是私有运行产物。

```bash
# 生成预览、自审、必要时最多重试两次；不会向正式名单发日报
python ai_daily_workflow/scripts/run_ai_daily.py prepare-reviewed --date YYYY-MM-DD

# 用户已授权的自动发布：生成、自审和审批通过后发给正式名单
python ai_daily_workflow/scripts/run_ai_daily.py publish-reviewed --date YYYY-MM-DD

# 根因修复后显式重开一轮
python ai_daily_workflow/scripts/run_ai_daily.py prepare-reviewed --date YYYY-MM-DD --rebuild

# 手动正式入口仍可用；自动发布会自行进入同一打包和投递流程
python ai_daily_workflow/scripts/run_ai_daily.py prod --date YYYY-MM-DD --skip-build --send --confirm-prod
```

工作日历、已发送期次保护和定时启动中午截止规则保持生效。`Restart=no` 防止 systemd 与应用级重试相乘；总服务超时为 6 小时。

兼容旧服务器：自动发送开启时，现有 `prepare --scheduled` 或 `prepare-reviewed --scheduled` 自动进入 `publish-reviewed`，不需要替换系统服务即可生效；关闭自动发送则退回自审预览。后续 `preview --scheduled` 遇到已投递期次直接跳过。若旧 systemd 单元仍有 `Restart=on-failure`，持久化预算仍将生成限定为 3 轮，成功告警也不会重复发送。仓库中的新单元定义供后续有管理员权限时安装。

本机制覆盖项目的预览生成与正式发送入口。手工从邮件客户端发出导出的 EML，或直接调用底层 SMTP 工具，不会自动执行这套编排，应使用上述正式入口。
