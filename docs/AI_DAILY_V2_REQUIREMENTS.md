## 1. 产品定义

AI 日报面向互联网公司产品、运营及相关中台岗位，在工作日上午提供一份可快速阅读、可追溯、经过 AI 编辑与人工审核的 AI 行业情报邮件。

它不是新闻搬运器，也不是每天必须填满所有栏目的内容模板。它需要完成三件事：

1. 从有限回看窗口中找出真正值得今天读的事件；
2. 将原始材料编辑为中文摘要、价值判断、工作启发及必要的边界提示；
3. 让编辑者可以低成本预览、修订、批准并可靠发送。

成功标准优先级如下：

1. 事实与来源可信；
2. 不漏掉明显高价值事件、不把低价值信息硬凑进日报；
3. 编辑结果对工作判断有帮助，不泄露网页原文、Prompt 或占位内容；
4. 制作、审核和发送状态可追溯且不会误发、重发；
5. 在守住上述底线后，尽量提高每日稳定生成率。

## 3. 范围与非范围

### 3.1 V2 必须覆盖

- 自动采集、人工补链与候选池管理；
- 高价值未发布候选的跨日重审、原因诊断、延期/放弃及发布核销；
- 来源分级、跨源合并、跨期去重与选源说明；
- 新闻逐条 AI 编辑、研究/工程/方法深度解析及栏目路由；
- 草稿独立 AI 审核、定向返工与最终邮件检查；
- 可选深度模块的图解生成、审核、压缩及 CID 内嵌；有图必须合格，无图允许以完整深度文本交付，不能保留断图或“如下图”之类悬空引用；
- 日期、版本、审批、预览、正式发送和逐人投递状态；
- 周邮件聚合；
- 反馈链接、投递分母同步和失败补偿；
- 运行日志、发布清单、版本与配置血缘；
- 本机/Codex 兜底产物的安全导入。

### 3.2 本轮不做

- 历史知识库或全量网页长期存档；
- 千人千面内容与按收件人改写；
- 根据反馈自动修改评分权重；
- 通用多智能体编排平台；
- 新建完整运营后台；
- 每类新闻独立工作流或大量类型特例；
- 无人值守地自动批准边缘新闻或研究图片。

## 4. 角色与运行模式

### 4.1 角色

- **系统**：采集、去重、调用模型、生成产物、执行确定性校验并记录状态。
- **编辑者**：补链、修订内容、处理边缘判断、预览并提交/批准正式 revision。
- **发布者**：执行正式发送、授权纠错重发或开启限时自动模式。小团队中可与编辑者是同一人，但权限动作仍需区分。
- **管理员**：维护密钥、收件名单、允许的模型/provider、部署版本和定时单元。

### 4.2 运行模式

1. **标准模式**：08:30 自动制作，编辑者审核后手动发布。默认模式。
2. **限时自动模式**：仅在明确的开始/结束日期内免人工点击；0–4 条新闻或任何硬阻断都必须中止当日发送。仅图片技术不可用时，允许按 10.2 自动改为无图深度文本并重新通过审稿与打包检查；图片质量不合格被撤下、来源只可自报、审稿不可用或结论待人工确认时，只交付待审预览。可以在选源前显式选择 `news_only`，但不能为了免审而静默删除已有高价值正文。
3. **人工兜底模式**：本机或 Codex 可补做文本/研究图，但必须导入候选 revision，经过相同校验与批准，不能绕过正式入口。

## 5. 核心对象与状态

### 5.1 日期与版本必须分离

- `issue_date` 表示日报日期。
- 编辑阶段使用一个带操作日志的工作草稿；重试、格式修复和被丢弃条目属于 `run_attempt`，不会各自制造 revision。
- 草稿首次形成预览、导入外部产物或提交审批时，冻结为不可变 `revision`；此后任何用户可见内容、来源、顺序、图片、模板或名单变化都创建新 revision。
- 同一日期最多一个当前有效、尚未发送的 approved release；新修改会使旧的未发送批准失效。已发送 release 永久保留。
- 每次正式发送引用一个不可变 `release_manifest`，不能仅引用某个可被覆盖的 HTML 文件。
- `issue_date` 在 release 中按 `Asia/Shanghai` 冻结；跨午夜重试不得重新计算日期。

### 5.2 最小主状态

```text
COLLECTED → SELECTED → EDITED → ASSET_READY/N_A → PREVIEW_READY → APPROVED → SENT
```

- 任一阶段可以产生 `BLOCKED` 结果及可操作原因。
- 已冻结 revision 不回退；修改从工作草稿形成新的 revision。
- `FEEDBACK_SYNC_PENDING / DONE / FAILED` 是发送后的辅助状态，不进入主状态链。
- 投递使用独立子状态，不把 SMTP 的不确定窗口硬塞入内容状态链。
- AI 审稿状态和图片跳过原因是阶段辅助记录，不再各造一套主状态机；`ASSET_READY` 表示选用图片已合格，`N_A` 表示明确无图，不表示待审图片通过。
- 日级状态由所有 revision 和正式发送记录聚合，不能通过“某个文件是否存在”推断。

## 6. 端到端工作流

```text
采集 → 候选池与事件合并 → 选源快照 → 材料包 → AI 编辑
     → 独立草稿审核（定向返工）→ 可选图解与实图审核
     → HTML/CID 与最终一致性检查 → 冻结预览 revision
     → 批准 release → 唯一发送入口 → 异步反馈同步
```

每个阶段只负责一种职责，并输出结构化产物。后续阶段不得通过猜测文件名恢复前置状态。

正文先审再生图，避免为不合格稿件浪费绘图调用；图像处理和不依赖图片的新闻排版可并行。终检只检查最终文字、图片和链接的一致性，不再无条件重写一遍全文。草稿修订不反复抓取全部来源或重生成已通过卡片。

## 7. 采集、来源与候选池需求

### 7.1 统一候选池

自动源和人工链接都必须进入同一个候选池。候选至少记录：

- 稳定候选 ID、首次发现时间、来源发布时间及其时区/可信度、可确认的实质更新时间；来源发布时间与聚合站收录时间分别保存，不互相冒充；
- 标题及 `evidence_sources[]`；每个证据源记录规范化 URL、来源等级、发现/一手/支持角色、抓取状态、发布时间及其支持的事实，并可指定一个 `primary_source_id`；
- 来源等级与来源类型；
- 事件指纹和跨源关系；
- 实际覆盖该事件的正式发布引用、未发布待办状态及历次选择/失败/延期/放弃原因；补漏状态附属于候选，不新建独立内容事实源；
- 抓取状态、材料摘要与证据边界；
- `selection_track`（时效动态/工程方法/研究前沿）、轨道资格理由、自动评分及入选/候选/合并/退出原因；轨道仅决定评选视角；
- `manual_add / adjust_priority / must_include / exclude / reorder` 等人工操作记录；排除必须注明 URL、事件或域名范围并可撤销。

### 7.2 来源等级

只保留四档，避免来源规则过度细分：

1. **一手来源**：官方博客、论文、文档、仓库、公告或当事方声明；
2. **可信直接信号**：已确认的官方/作者社交账号；
3. **可信二手来源**：具备明确事实引用和可核对信息的媒体；
4. **发现源**：聚合站、早报、综合稿、转载或线索帖。

发现源用于发现，不应自动成为主要事实来源。若无法解析到更高等级来源，系统可以保留为候选，但必须降低置信度并进入人工判断。

### 7.3 最低证据要求

- 模型发布、重大安全事件、法律诉讼、公司重大经营数字必须有一手来源或至少两个相互独立的可信来源。
- 普通产品技巧与低风险动态可以基于一个可信二手来源，但要保留边界提示。
- 原文不可访问时，不得把聚合摘要扩写成材料中没有的新事实。
- 原文、官方索引、聚合摘要的材料完整度分别记录。同一事件合并时逐字段保留更可靠、信息充分且无冲突的证据；不能因官方索引等级较高，就用只有标题和日期的短文本覆盖全部已有材料。
- 若发布时刻只能精确到日，记录日期精度及来源时区的已知范围；按可能时间区间判断窗口相交，必要时复核文章页。不得将本地零点伪装成已验证的精确发布时间，从而误排窗口边缘条目。
- URL、发布日期、来源关系由确定性代码维护，不交给模型编造。
- 预览和正式邮件中每条内容至少展示一个可点击的规范来源；依赖多源核验的高风险内容在审核视图中展示完整证据链。

### 7.4 去重

- 跨期去重只以**正式已发送 revision** 为历史基线。
- 未发送预览、失败稿、候选稿不得污染未来选源。
- 已发基线只包含实际渲染并正式发布的事件和来源身份；`dropped_cards`、生成日志、审核备注和候选附件不计作报道。发布时冻结正文 hash、实际卡片/事件 ID 与经核对的来源别名；不能在次日递归扫描可覆盖的草稿文件推断已发。
- 同一事件的多篇来源合并为一个候选，并优先保留最高等级来源。
- 事件归并以主体、动作、对象和新增事实为依据；标题不同、来源不同、栏目建议不同不能让同一事件拆成多张卡。先合并证据，再排序与编辑；编稿后再检查一次重复。
- 同一事件的媒体报道、当事方回应和措施通常合并在一张卡中，标明事实与说法的区别。官方声明是一手立场，不能自动证明所有争议事实；独立可信来源的证据仍保留。
- 同公司/同产品的新进展可独立保留，例如模型首次发布与随后企业平台开放；需记录相对已发内容的新增事实。疑似重复只提示人工确认；已确认重复必须合并或移除后才能批准。
- 人工可以“本期保留”或“永久排除”，操作必须留痕。
- 规范化 URL 须覆盖域名迁移、跟踪参数、arXiv 的 abs/pdf/html 与版本号，以及同一 X 状态的账号路径和 `i/web/status` 路径。来源身份相同不代表不同事件相同；一张卡仅报道综合早报的一项事件，不能把整篇早报其余事件一并标为已发。

### 7.5 人工补链契约

- 人工输入一个或多个 URL，默认只执行 `add_candidate`，不等于强制入选；可附建议标题、类型、补入原因和补充一手来源。
- 系统必须返回 `new / merged_duplicate / already_sent / unfetchable / needs_evidence` 之一，并执行与自动候选相同的来源解析、判重、材料抓取、AI 编辑和质量门。
- `must_include` 是独立操作，必须记录原因，但不能绕过证据要求、重复检查、新闻上限或 AI 编辑。
- 人工补链抓取失败时，可以补充另一条可核对来源或材料；不能仅凭人工断言扩写。
- 预览或批准后补链会产生新 revision 并使旧的未发送批准失效；正式发送后默认进入下一期，除非走纠错重发流程。

## 8. 选源需求

### 8.1 价值判断

系统综合判断以下四项，不将任何单一热度分直接等同于入选：

- 对目标读者的工作相关性；
- 事件的新颖性与实际影响；
- 证据质量与可解释程度；
- 与当期其他内容的重复度。

数量、栏目均衡、阅读时长和来源多样性是软偏好，不得为了满足配额牺牲新闻质量。

### 8.1.1 三轨选稿，共用一条编辑链

先判断候选适合哪种阅读价值，再在同轨内比较；综合分不作为跨轨的统一资格门槛。三个轨道不是新增栏目，也不是三套采集器、模型或工作流。

| 内部轨道 | 资格与比较重点 | 默认处理 |
| --- | --- | --- |
| 时效动态 `timely_news` | 已发生的具体新变化；比较时效、影响、对目标读者的意义和证据。涵盖产品、模型、商业与安全动态，不仅限于重大突发 | 优先交代变化与可用范围；保留实际增量 |
| 工程方法 `durable_method` | 可靠且可追溯的来源、明确工作问题、可解释的方法机制、足以复用或评估的具体材料 | 普通新闻形态默认倾向选 0–2 条，计入新闻 12 条上限；深度形态只占深度名额 |
| 研究前沿 `research` | 按 10.1 的机制、证据、边界与深读价值要求判断 | 与工程/方法候选竞争同一个可选深度位置，不独占图解资格 |

工程方法的具体材料可以是架构、算法、代码、数据、可复核案例或部署经验；这些是证据示例，不机械要求“必须有两种附件/两次关键词命中”。普通宣传、泛泛建议、仅标题或代码堆砌不能获得资格。一手厂商来源证明出处，不等于其效果主张已获独立验证。

一篇文章只保留一个主要轨道。轨道表达内容性质，`presentation` 仅区分 `news_card / deep_feature`；工程方法可以保持原轨道并提升为深度呈现，不必冒充论文研究。它不能同时占用新闻与深度名额，也不因有代码、架构图就强制生图。普通卡片按 8.3 路由，例如 AgentCore 记忆治理通常进入“智能体工程”；达到深读准入且解释收益突出时可进入“前沿与实践”。

分数用于轨内排序与解释。重大动态多时允许工程方法为 0；方法内容突出时编辑可保留超过 2 条并记录理由，只受新闻总上限和统一证据规则约束。不设“动态至少 3 条”或“每天必须有方法”的硬配额。

### 8.1.2 有限的编辑复核与失败处理

- 对事件合并后的拟入选稿与边缘候选做一次有界 AI 比较，重点检查独立信息增量、受众价值、证据和栏目；工程方法须有独立候选名额，不能先被全局总分淘汰后才复核。
- 第一版默认每轨至多复核前 5 个事件及人工标记必选项；超过预算的候选保留并显示“未复核”，不静默当作低质量淘汰。预算是版本化运行配置，不是发布条件。
- 输出只保留“入选、留候选、合并、退出”和一句依据，引用已有候选/证据 ID；栏目与必要的轨道修正复用现有字段，不新增长篇逐项评分 Prompt。
- 复核复用材料解析/编辑阶段，正常只做一轮；修订后仅重新检查受影响项。复核超时或格式失败沿用 9.3 的有限处理，不重跑整期；保留候选建议和未复核警告供人工审核。限时自动模式下需人工判断的普通项退出当期，必选项按原规则阻断。
- 工程轨道为空、评分偏低、复核预算用尽均不单独阻断预览；确定的事实、证据、重复和发布问题仍按统一质量门处理。

### 8.2 断档补漏

- 每次运行冻结采集截止时间 `T`。时效动态默认回看 `[T-48h, T]`，工程方法默认 `[T-96h, T]`，研究默认 `[T-72h, T]`；未发送候选可在有效窗口内重新参与选稿。
- 从最近正式已发送 release 取得其选源覆盖截止 `C`，不是 SMTP 发送时间。若 `T-C > 48h`，时效动态扩展到 `[max(C, T-96h), T]`；无可信 `C` 的首次运行或迁移期，保守回看 96 小时并提示基线缺失。窗口边界允许重叠，由事件去重消除重复。
- 例如周五 08:30 选源、10:32 发信，周一应回看到周五 08:30；08:30–10:32 的消息不能因在发送前出现就丢失。已核对覆盖不代表所有网站均抓取成功，源健康度必须同时显示。
- 扩展窗口统一传给 AIHot、BestBlogs 和官方源。窗口内先入候选池再按轨道判断；取消仅限模型/安全事件且需 86 分的补漏入口。不会因超出常规 48 小时就提前抹掉工程、产品或企业应用候选。
- 同一来源包含多种内容时，先按本次各轨道所需的最早起点采集，再解析轨道和执行对应时效规则，避免先用 48 小时过滤导致方法轨道没有机会识别。候选元数据与去向至少保留覆盖自动回看和必要去重的时间；不要求长期保存全量网页。
- 滚动 RSS 可能只含最近若干条；必须记录原始条目数、时间覆盖和抓取状态。若未覆盖所需起点，使用已有候选、站点历史入口或一手列表进行有界补抓；仍不足则显示“覆盖不全”及缺失区间，不能宣称补漏完整。无需首版增加全网爬虫或周末高频任务。
- 新发现但发布时间较早的条目、日期不明确的条目和实质更新单列为待复核候选，保留真实时间，不能用发现时间伪造新发布；超出自动窗口的人工补链注明补入理由。不把抓取延迟自动解释为内容过时。
- 断档超过 96 小时须明确显示未自动覆盖的较早区间，由编辑决定是否专项补漏；不宣称长假内容已全部覆盖。
- 每条已解析条目都留存最终去向：入选、留候选、已发/同事件合并、超窗、证据不足、抓取失败或未复核。评分前过滤也留理由；补漏用于发现遗漏，不用于凑够篇数。

### 8.2.1 高价值未发布候选闭环

采集回看解决“这次去哪里找”，补漏队列解决“已找到的内容后来去了哪里”；两者共同工作，不能互相替代。补漏是 `candidate_pool` 的附属状态与可重建视图，不新增一套独立选源器、发送入口或定时任务。

- 已选中但未进入正式发布的条目、人工标记需跟进的条目，以及通过轨道资格且被评为高价值的未入选候选进入补漏视图。生成失败不等于价值低，来源待核验不等于已经否决。
- 默认活动重审期为首次发现后的 7 天，每次最多召回 12 个历史事件进入原有选源/编辑链；优先处理生成失败、人工待办与高价值未发布项，兼顾等待时长。预算用尽的条目保持未复核状态，不静默丢弃或提高其分数。
- 重审期、召回预算是版本化配置，原始发布时间不变。超过常规采集窗口仍可作为补充参与复核；超过活动期转为到期待审并保留最小元数据、原因和历史引用，编辑可延长、延期或明确放弃。到期不等于已报道，也不要求长期保留全量网页。
- 候选去向至少区分：待复核、来源待审、生成失败、草稿就绪、已发布、明确放弃、到期待审；延期记录下一次复核日期。放弃/延期必须有原因及操作者；重新抓取或重算评分不能覆盖人工决定。
- 当期卡片 `DROPPED` 只表示退出本次制作；符合上述条件的候选仍以生成失败或待复核状态参与下一期。重审继续遵守来源证据、三轨资格、重复检查、数量上限和总调用预算；不自动触发邮件发送。
- 草稿、预览、批准但未发送均不核销。已发布状态引用正式 release 的实际卡片/事件身份；发送中、部分成功或状态不确定的 release 继续受投递保护，不通过补漏另建一封邮件重复发送。
- 最终预览形成后，对比拟入选/人工必选、补漏候选与实际正文，记录每条缺项的原因和后续动作。高价值普通项未入正文须可解释，人工必选未解决沿用批准阻断；不是要求把所有高分项都塞进同一期。
- SMTP 已接受的事实不因补漏视图更新失败而回退；从不可变发布快照补算，不能重发邮件来修复队列。历史发送记录缺少实际正文或可信版本时标为基线待核对，不从生成元数据猜测已发。

现有生产迁移实现用“已选中，或原始新闻分至少 80，或具研究资格且研究分至少 65”收集待办；这只是旧评分体系下的队列入口，不是 V2 三轨准入线或自动保送线。原始分、来源封顶后的有效分和最终编辑判断分别保存；升级后不得继续用统一 80 分门槛挡住合格工程方法。

### 8.2.2 用户补链与漏报原因诊断

当编辑者提供链接询问“漏掉了还是分数不足”，先用对应日期的采集、选源、生成与发送快照还原事实；必要时再抓取当前网页补证，两类证据明确分开。

| 阶段 | 必须能回答的问题 |
| --- | --- |
| 发现 | 当时是否抓到？哪个源/快照、首次发现时间、来源覆盖是否完整？没有留存证据则标为未知，不能断言未抓到 |
| 过滤与合并 | 是否超窗、误判重复、路由错误、解析失败或并入另一事件？指出实际规则、匹配对象与原始时间 |
| 评分与排序 | 原始分、有效分、封顶/扣分、轨道资格、排序/预算及是否复核；区分“分数低”和“受来源门槛限制” |
| 编辑 | 是否已选中、抓取成功、生成失败或被人工移出？保留失败字段、attempt 与具体理由 |
| 发布 | 是否出现在最终正式卡片中、使用哪个一手链接、属于哪个 release？只在草稿里不算已发 |
| 后续 | 已合并、已发布、补入候选、待来源核验、延期、放弃或继续待审；给出可执行动作 |

诊断按事件关联用户链接、聚合条目、一手原文和最终卡片，不能只查 URL 字符串是否出现；存在官方原文但最终用官方社交声明报道时，要指出“事件已覆盖、来源可以升级”。历史没有评分则显示未评分/未知，当前重算作为新的评估记录，不倒填历史，也不把用户补入等同于必须入选。

### 8.3 六个最终板块

V2 使用一个可选的“前沿与实践”深度模块和五个互斥新闻栏目，仍是六个展示板块，不是每日必须填满的配额。原“研究前沿”升级为深度模块展示名，子标签区分研究解读、工程实践、方法技巧，避免把教程包装成研究突破。每条内容只出现一次；空栏目不渲染。

1. **前沿与实践**：有可解释机制、可核对证据和适用边界，值得深读的研究、工程案例或技巧方法；有图/无图是呈现选择，不是内容类别；
2. **模型更新**：具体模型、权重、API、推理能力或正式能力版本发布；
3. **智能体工程**：Agent 架构、工具链、协议、评测、训练或安全工程；
4. **产品与入口**：面向用户或企业工作流的产品能力、分发入口与生产力应用；
5. **行业动态**：商业、政策、市场、版权、组织、安全事件及生态变化；
6. **技巧与观点**：可复用方法、评测方法、实践指南与有证据支持的行业观点。

“公司收入上升”“模型支出偏向低成本选项”“搜索入口渗透率变化”不能仅因提到模型而进入“模型更新”。产品发布与分发入口合并为“产品与入口”，不再维护两套高度重叠的分类。

路由以“事件实际改变了什么、主要服务谁”为准：命名模型/权重/API/正式能力版本进入模型更新；开发者侧 Agent 架构、协议、工具链、评测、训练或安全方法进入智能体工程；终端用户或企业工作流产品及分发入口进入产品与入口；商业、政策、版权、组织、市场和事件型安全新闻进入行业动态；可复用教程、方法和有证据的观点进入技巧与观点。

### 8.4 数量、阅读与来源覆盖

- 新闻数指最终 revision 中去重后、已完成编辑并进入邮件的新闻卡片数，不含深度模块；研究/工程/方法都共用这一个深度名额。延续原配额：最多 12 张新闻卡加 1 篇深度内容，不是新增第二个图解名额。
- 0 条新闻硬阻断；1–4 条可生成预览，标准模式须显式确认低条数后才能批准，限时自动模式不发送；5–10 条为目标；11–12 条允许批准但显示阅读时长警告；超过 12 条不可批准。人工补入同样计入上限，不得静默截断。
- 默认总阅读时长软预算为 10 分钟，超出只警告，不自动删稿。
- 同等质量下，产品入口、运营提效和真实工作流内容优先于重复的第三、第四条同类 Benchmark/基础设施新闻；此项只影响排序，不降低准入线。
- 工程方法的 0–2 条是新闻组合偏好，与栏目配额分离；提升为深度的条目不重复计入新闻数，也不强制补齐腾出的名额。深度没有入选时，不自动补一篇低证据图解或扩大新闻配额。
- 自动运行绑定版本化 source registry，并输出预期、成功、失败的源及候选数量。单源失败只警告；新闻源整体不可用或一手来源解析能力整体失效时，限时自动模式不得发送。

#### 8.4.1 独立发现与来源健康度

- 聚合发现、一手官方列表与定向论文发现互为补充。新增来源必须记录覆盖主题、解析器、数量/时间上限、原始条目数、解析/匹配数和最后成功时间；有 HTTP 响应但解析为零不能自动认定当天没有新闻。
- 来源缺失、抓取失败、列表发布滞后、滚动窗口截断、日期解析失败和信号匹配为零分别显示。短期异常只提示并继续其他源，不为“零候选”无限重抓；内容确为空可记录正常空结果，但必须有依据。
- 适配器测试覆盖当前与历史域名、相邻日期元素、RSS/Atom 及论文原始提交时间；聚合榜单域名迁移后仍能用稳定条目 ID 匹配。官方社交账号身份与状态 ID 分开保存；短链或 `i/web/status` 丢失账号不自动等于非官方，须用可信证据恢复身份，无法确认则标为待核验。
- 当前修复提供 Google Developers 直接采集、OpenAI 官方更新回看，以及 arXiv 的定向发现；具体 URL、查询条件和上限归 source registry 管理，不复制到 Prompt。V2 仍按 8.2 的统一轨道窗口执行，不将当前来源特定的 72 小时配置误称为完整窗口迁移。
- 已验证的 arXiv 初始查询覆盖 cs.AI/cs.CL 中标题含 agent、agents、memory、evaluation、reasoning 的最新 120 篇；原始提交时间继续过滤到研究窗口。这个上限与关键词只定义覆盖边界，不承诺所有论文都能召回；DAIR 周刊列表未更新也不作为当天无论文的证据。
- 调整来源/规则后用既有漏报样本回放，比较召回增量、误选、重复与运行成本；不为通过某篇文章给特定作者、厂商或 URL 免审资格。

## 9. AI 编辑需求

### 9.1 职责边界

模型负责：

- 中文标题与摘要；
- “值得关注”；
- 面向产品/运营的工作启发或行业视角；
- 必要的边界提示；
- 语义分类建议。
- 候选的轨道资格、事件合并及信息增量建议；必须基于已抓取材料，输出有限且可追溯的判断。

确定性代码负责：

- 日期、URL、来源、候选 ID 和版本；
- URL/ID 等精确去重、执行语义归并和栏目决策、数量上限；事件语义和分类不能只靠关键词命中，疑似关系交给模型或编辑复核；
- JSON Schema、空字段和非法字符校验；
- 模型/provider 身份、调用结果与发布状态；
- 邮件打包、CID、名单和幂等发送。

### 9.2 新闻卡片最小输出

每条新闻只要求以下内容字段，不设置机械的精确字数：

- 中文标题；
- 事实摘要；
- 值得关注；
- 工作启发或行业视角；
- 可选边界提示；
- 栏目建议。

不得出现 Prompt、GitHub README/网页大段原文、HTML 残片、占位标题、无法解释的英文正文或模型自述。

期级内容保留“今日编辑简评”和“今日小结”，只基于最终入选材料生成并支持人工编辑；不得为了制造统一叙事而强行串联无关新闻。

Schema 只承担传输契约：核心必填字段非空、类型正确、JSON 可解析且无危险控制字符；`boundary_note` 可空，栏目建议使用五个新闻栏目枚举。长度、中文比例、措辞和一般信息密度属于软检查，不应因合法英文缩写、模型名或罕见字符误杀整条内容。

- 英文论文名、模型名、基准名与中文叙述可以共存；不能按拉丁字母数量把正常中文稿判成英文原文泄露。纯英文搬运、网页导航和占位稿仍按内容问题处理。
- 事实摘要回答发生了什么，价值说明解释为何值得关注，工作启发给出适用判断或具体检查方法；三个字段不能同义反复。优先短而有信息量，不强制精确字数，也不靠泛化风险段落填充。
- 实际编辑输入须包含有界的一手证据片段及其引用/抓取状态，只有标题或索引时应显式说明材料不足；不要求模型仅凭回退摘要完成事实核验。
- 补报保留真实首发时间，并在必要时使用“重要补充”等读者能理解的标记；生成失败、分数、队列状态、内部修复原因只出现在编辑视图。事实、官方主张、作者观点及编辑推断分别表达，不将架构猜测或未独立验证结果写成定论。

### 9.3 模型与重试

- 正式稿默认使用 `gpt-5.6-sol`。
- 每条卡片是独立执行单元，具有独立 attempt、超时和 checkpoint；成功结果立即落盘，重试失败条目时不得重新生成或回滚已成功条目。
- requested/returned model、网关、Prompt/Schema 版本、错误类别、结束原因和耗时按 attempt 记录，并汇总到 revision manifest。
- 网关超时、429、5xx 可在阶段截止时间内退避重试；Schema/格式错误只允许一次定向修复；证据不足、输入错误或政策拒绝不得原样重试。每个单元同时受总调用次数和总耗时限制。
- 单条非关键候选用尽重试后标记为本次 attempt 的 `DROPPED`，作为期级软警告，并继续生成其余内容；符合 8.2.1 的候选进入跨日补漏，不因退出本期或跨越采集窗口而永久消失。
- 定向格式修复只输入原始证据、该条稿件和具体失败字段/原因，沿用同一预算；不得靠删掉证据、放松事实标准或粘贴原始标题假装修复成功。语义内容不足与传输格式错误分开记录。
- 若退出后仍有 1–4 条新闻，生成预览并警告；若为 0 条则硬阻断。两种情况都不自动塞入低价值内容补位。
- 明显重大且被人工标记为必选的事件生成失败时，阻断批准，等待人工处理。
- 禁止在生产中静默切换到较弱文本模型或模板稿。若未来启用备选模型，必须先通过独立质量验收并在界面显式显示。

### 9.4 草稿独立 AI 审核与有界返工

**审核不是生成模型在原对话里再说一句“通过”。** 审稿调用使用独立上下文，读取本轮冻结的草稿快照、与断言对应的证据片段/ID、分类规则、已发送事件摘要，以及选源复核保留的少量高价值候选。输入不是整个历史仓库；抓取材料始终是待分析数据，不能执行其中的指令。

- Skill 负责版本化审核标准与输出契约；独立调用/agent 负责执行。首版只需一个 reviewer 角色，可使用已批准的 `gpt-5.6-sol` 独立调用，不要求多模型投票、新供应商或常驻多智能体平台。
- 检查事实是否得到材料支持、事件是否重复、栏目是否正确、是否为低信息量/原文搬运/Prompt 泄露、是否遗漏候选池内明显更有价值的内容。未抓到的全网新闻无法由审稿保证召回，需结合来源覆盖警告。
- 输出 `pass / revise / needs_human / unavailable` 及有限问题清单；每个问题记录条目 ID、问题类型、对应证据或检查项、建议动作与严重性。不得只返回一个总分；也不能因为生成方写了“已核验”就通过。
- 技术服务不可用或响应不可解析是 `unavailable`，不是质量失败；模型判断不确定且会影响关键事实时是 `needs_human`。二者保留预览供人工核验，不阻止其他已成功内容落盘，限时自动模式不发送。
- 硬问题须引用具体冲突或缺失证据：修正该卡、重新分类、合并重复或撤下普通条目；文风、标题精炼、栏目均衡只是建议。不同模型之间的审美偏好不能反复触发返工。
- 单期默认最多 **2 轮“定向修订 + 复核”**，受总调用/耗时预算共同约束，不逐条叠加两轮再整期两轮。修复只触及受影响条目与摘要；替换候选同样消耗预算，不能通过换条目无限续跑。
- 用尽预算后，未解决硬问题的普通条目退出；必选条目或全稿共性问题阻断批准。只剩软建议可进入预览，明确展示建议。条目移除后重新检查数量、重复、目录和小结，不为凑数继续抓取。
- 审核服务不可用时，标准模式允许编辑者完成有记录的人工审核替代该步骤；不得伪造 AI 审核通过，也不能用人工备注豁免仍存在的事实、血缘或打包硬问题。
- 审稿保存输入快照 hash、规则版本、调用身份与返回结论；它附属于草稿/内容产物，不另建一种核心产物。编辑者接受建议后的最终内容必须被对应审核覆盖。材料或正文变化使受影响审核失效；最终预览生成前汇总覆盖状态。

### 9.5 快速、精准、稳健的执行预算

- 先做便宜的字段、来源、精确重复和禁用内容检查，再做语义审核；不要花一次完整模型调用来检查 URL 是否为空。
- 抓取、逐卡编辑可有界并发，初始并发量由网关限流与服务器资源校准；不增加每天固定必须调用的模型数量。
- 每个调用只有一个重试预算所有者；SDK、网关适配器和调度层不得各自独立重试放大。格式修复计入同一预算。
- Checkpoint/cache 按材料快照、编辑输入、模型/provider、Prompt/Schema/规则版本建立键；全部相同才可复用。修改一张卡不使其他卡失效，但其相关期级摘要和审核须更新。来源实质更新、证据变更或模型配置变化不得误命中旧缓存。
- 全稿复核只做一次初审及有界增量复核；选源比较与全稿审查读取共同候选证据，但保留独立任务边界，不重复生成大篇评分理由。
- 先保留现有正确功能，再替换边界模块；不为速度省略关键证据核对，不为稳健把软偏好改成硬门。阶段超时交付已完成的待审预览，而不是假装整期成功或清空成功结果。

## 10. 前沿与实践：深度内容、Visual Handoff 与图解

### 10.1 深读与图解分别准入

深读必须具备：对目标读者有意义的问题、可解释的核心机制、至少一条可核对证据、明确范围/局限，以及足够的信息密度。证据可以是研究实验，也可以是公开架构、参考代码、完整方法步骤或可核对案例；不能把参考实现直接写成生产效果证明。

- 研究解读、工程实践、方法技巧使用同一准入逻辑，不要求每篇都是新论文。仅“AI 解出一道题”“单点榜单提升”“热度很高”不足以入选。
- 图解另问一个问题：画出架构、机制、对照或决策关系，是否比同样篇幅的文字更容易理解？没有解释增益则保留文本，不为增加视觉元素强制绘图。
- AWS AgentCore 记忆生命周期、电商 Agent 架构等类型可以参与深度候选比较；是否入选取决于当期实际抓到的材料，而非给文章/厂商免审资格。
- 日报可以无深度、深度无图或深度有图；三者都是完整产品形态。无图不意味着可以用短摘要或免责声明填充正文。

### 10.2 来源与图片兜底分离

- 首选深度材料抓取失败时，依次尝试下一合格候选，最多 3 个；不得拿聚合标题扩写正文。无可用候选则正常生成纯新闻版，不降低深读准入线。
- 本次图片调用计划从已批准 registry 中冻结，默认主线路加至多一个备选，不等于互联网上所有服务。技术故障按错误类型有限重试/切换；全部计划线路不可用时记录 `skipped_unavailable`，技术尝试因总预算结束则记录 `skipped_budget`，保留合格深度文本。未尝试的线路不能记为已证实不可用；两种技术跳过都适用同一无图版审核规则。
- 无图版删除图片占位、图注、图中引用及对应 CID，必要时把只有图里才有的关键解释补入正文；重新做受影响的审稿与终检。在编辑预览显示“未配图及原因”，不在读者正文泄露网关错误。
- 图片画错、文字乱码、边界越界是质量问题，不伪装成服务不可用。最多做一次定向图像修复；仍不合格则撤下该图并记录 `omitted_quality`，生成待人工审核的无图版。正文也有事实问题时仍须修复或撤下内容，不能借“跳过图片”放行。
- 政策拒绝不得靠换网关规避；保留拒绝分类，不原样无限重试。未批准的新模型/线路、Codex 本机补图和确定性替代图都不能被后台临时冒充为原计划成功；外部补图按 10.5 导入。
- 默认每期图像生成调用总上限为 3 次，包含重试、备选与质量修复，另有总耗时上限；这是可版本化运行预算，不是必须生成 3 张。无效凭据/余额不足等不原样重试；服务短期熔断须有新鲜失败记录和恢复探测机制，不能凭旧故障永久跳过。

### 10.3 保留固定流程，不强制一种绘制后端

```text
证据快照 → 编辑解析/深读正文 → Visual Handoff → 编译后的实际 Prompt
        → 受控生成 attempt → 原图 → 可选派生/压缩 → 最终图审核 → 发布绑定
```

解析沿用 `ai-frontier-brief-editor` 的好部分：先解释来源，再分离邮件正文与 Visual Handoff；只把绘图所需信息交给画图后端。生图沿用现有 skill 的候选、实际看图、定向修复、暂存、CID/压缩和血缘思想。服务器通过受控 adapter 执行同一契约，不能只在 Prompt 中写“请使用某 skill”就认定调用了流程。

绘制路线由内容决定并记录，不用“出现中文/超过三个标签”机械决定：

| 路线 | 使用条件与要求 |
| --- | --- |
| 原生生图 `model_native` | 以用户已认可的原生图解为质量基线，适合机制/架构解释；模型可以同时绘制文字与结构，最终逐项检查关键标签与关系，不默认只让它画底图 |
| 混合 `hybrid_overlay` | 精确文字/数值排版确有必要，或已出现原生文字错误时采用；须保存原始底图、文字清单与渲染规格，仍要审核最终图，不能把“文字是代码画的”当作整体合格 |
| 确定性图表 `deterministic_chart` | 证据本来就是精确数据表/关系图且有解释增益时使用，明确标注渲染路线；图片服务全不可用时默认不自动用简陋绘图顶替，而按无图策略处理 |

白色主背景是已确认主题，允许浅色分区和少量语义强调，禁止黑色或大面积深色底。以一个清楚的解释中心组织必要信息；保留机制、证据和范围，但不把它们限定为三个孤立图标。“约 8–12 个短标签、2–3 条结果线索”只能是创作参考，既不是最低密度也不是硬上限；复杂内容优先保留理解机制所必需的组件与关系，删除装饰和重复结论。

### 10.4 精简 Visual Handoff 契约

**六个语义字段，元数据放旁边，通用风格只定义一次。** 字段用于组织信息，不要求每格一长段，也不强制精确字数。初版以一屏可审阅为目标，超长先提示压缩重复项，不能截断关键机制或直接让生成失败。

| 字段 | 必须回答的问题 |
| --- | --- |
| `subject` | 这篇讲什么？包含对象和面向读者的短标题，不复制聚合站标题 |
| `takeaway` | 读者最应该理解的一个结论或问题是什么？保持原证据强度 |
| `mechanism` | 哪些组件/步骤构成机制，怎样连接，输入与输出是什么？写清分支、反馈或对照，不把名词列表冒充机制 |
| `evidence` | 用什么材料支持它？选择能说明问题的证据；准确数字须带口径，无数据就不画假曲线/伪比例 |
| `scope` | 哪些场景成立，哪些不能推断？只写这篇特有的重要边界，不堆通用免责声明 |
| `labels` | 必须保留的标题、关键实体、数值/单位及可精简说明；区分需精确一致和可同义改写的文字，不重复塞入全文 |

附属元数据保存在同一内容/资产记录中：证据 ID/断言映射、输入 hash、handoff Schema/解析规则版本、风格版本和绘制路线。标识、文件路径、hash、调用日志和审核规则不进入画面，也不全部发送给生图模型。没有数字/副标题时留空即可，不要求编出内容补齐。

Prompt 编译只有一个入口：`六字段内容 + 版本化短风格规则 + 路线必要指令`。标题和禁止项不在前后重复三次；provider adapter 只转换请求格式/受支持参数，不私自改结论、删除证据或追加另一套审美规则。若必须转换 Prompt，保存转换前后及最终实际外发文本；不静默截断。

通用规则只保留：白底与邮件可读性、清楚的信息层级、不编造事实/数字、不以装饰暗示未经证实的能力、遵守标签和范围。旧的 `Avoid / Reject If / Do Not Imply / Must Preserve / Complexity Budget` 等重叠项在迁移时分别并入风格规则、`scope` 或 `labels`；不是机械删字段后遗失原要求。

Handoff 进入生图前检查四件事：主题/证据是否同源、机制是否可读、标签与数值是否有据、是否自相矛盾。Schema/空核心字段由代码检查，语义问题复用深度编辑审核。只允许一次定向修复且计入编辑预算；不因文风、标签数量或一般布局偏好反复返回解析。

### 10.5 怎样验证“确实走过我们的工作流”

必须区分三件事：**流程执行可追溯、产物没有被替换、图像内容合格**。它们分别检查，不能互相代替；文件名、目录、修改时间、`source_kind=imagegen`、`review_status=pass` 都不是独立执行证据。

| 关口 | 由系统核验的依据 | 失败后的范围 |
| --- | --- | --- |
| 输入与编译 | 证据快照 → brief → handoff 的引用与 hash、解析/编译/风格版本；实际请求使用的 Prompt 与编译结果一致，转换有记录 | 停止该图的生成或采用，修复受影响的输入，不重跑整期抓取 |
| 实际调用 | 受控执行器在请求前创建 attempt；请求后记录成功/失败、endpoint registry 快照、requested model、returned model（如有）、请求/响应 ID（如有）与实际输出 hash | 无可信调用记录则不认定为本流程已验证产物 |
| 派生与最终资产 | 原图、混合叠加/压缩步骤、参数与输出 hash 串联；最终邮件引用资产与审核目标相同 | 拒绝该资产，不能修改 manifest 来迁就替换后的文件 |
| 质量与发布绑定 | 审核读取实际最终图及对应 handoff/证据，记录问题、规则/审核者身份和目标 hash；release 引用同一图及审核记录 | 未完成审核的图片不可发送；可按 10.2 撤图形成新待审版本 |

实现边界：

- 解析指令、必要 skill/reference 内容、编译器、风格与 Schema 随只读 `workflow_bundle` 统一版本化，执行器实际装载该版本并留 hash；禁止仅填写 skill 名称而实际调用另一份未登记 Prompt。服务器与 Codex 可使用不同执行适配器，但共用契约与黄金输入验收。不试图证明模型“理解了所有 skill 指令”，而是证明系统实际提供了哪些输入、执行了哪些步骤，再审核输出。
- attempt 和审核记录由相应受控执行器写入服务器账本，生成内容或导入包不能自行写“通过”覆盖它们。普通制作进程不能修改发布批准；无需新分布式平台，首版用事务账本、文件权限与不可变产物即可。
- 生成记录不仅在成功后写文件；请求前即落 intent，失败也留记录。外部 request ID 缺失不单独判失败，但必须有本机受控调用记录，并标明哪些身份只能由 registry 推定。
- 网关未返回实际模型时标为 `not_reported`；requested model 和已批准线路仍可核对。模型不一致/返回异常进入待人工确认，禁止把配置模型名冒充上游返回。除非上游提供可信证明，系统无法保证网关内部真的运行了哪个权重，也不能抵御拥有服务器管理员权限的人篡改；不承诺“绝对证明”。
- 单独重新计算所有 hash 只能证明文件彼此一致，不能证明真实执行。因此账本中的 attempt、调用权限与独立审核必须来自受控入口，不接受任意 JSON 自证。
- 本机/Codex 补图按相同字段导出可移植包，包含输入、原图、实际工具输出关联（可获得时）、派生资产与审核证据；服务器重新计算 hash。无法独立核实的调用来源标为 `self_reported`，可经人工看图和来源确认后采用，但不能改称 `runner_verified` 或进入无人值守发布。
- 旧 manifest 可以只读回放；新生产候选必须满足 V2 契约，不允许通过改成 schema v1、切换 policy 字符串、`--allow-*` 或复制旧批准记录绕过校验。本地绝对路径/时间戳只辅助定位，不作为服务器可移植性的前提。
- 正文、handoff 或证据语义变化会使相关图片审核失效；Prompt/资产变化使对应血缘检查失效。缓存复用须引用原可信 attempt 并通过新版本的适用性检查，不凭文件名复用。

### 10.6 审查实际图片，而不是“有一张图”

- 机器先检查 MIME、可解码性、尺寸、文件大小、路径/CID 与 hash。随后由能读取图片的审核调用或人工查看**最终压缩图片在邮件展示尺度下的效果**，同时对照 handoff 和关键证据。
- 核验关键文字/数值、箭头与因果方向、机制组件是否遗漏、证据口径/范围是否被夸大，以及是否可读。OCR 可帮助定位错字，不能证明图正确；无法可靠识别的重要文本交人工确认，不因一次 OCR 误读直接否决整图。
- 不使用“验证通过”、认证盾牌等超出材料强度的表达；也不能无证据画上升条形图暗示量化改善。没有量化数据时用机制或明确的非定量对照，不创造实验结果。
- 事实错误、关键标签乱码、主体/机制画错或违反明确白底主题，使**该图**不合格；一般信息密度、配色细节、装饰偏好只提出建议。不是所有“不够好看”都触发重绘。
- 视觉审核者必须取得图片输入；纯文本模型仅审 Prompt 不算实图审核。未配置可用视觉审核能力时，标为待人工看图；不自动换到新服务，不伪造审核通过。
- 混合路线同样检查箭头是否指错、文字与底图是否错位；确定性绘图同样检查事实。审核不以 provider 名气、分辨率或文件大小代替实际质量。
- 审核对象是最终发送资产。压缩后字糊须修复压缩/尺寸并复检，不无谓重画原图；格式重编码、加标签或替换图片后重新检查受影响资产。冻结 release 后不再改变图片字节。

## 11. 预览、审核与发布需求

### 11.1 固定预览入口

- 不传日期时查看当日日报；传入明确日期时查看对应日期的最新可预览 revision。
- 审批预览必须由将要发送的同一内容、模板、最终资产和名单快照生成；个性化 token 可以脱敏，但必须完成实际替换校验。
- 预览必须显示：日期与期数、revision、主题与周会话键、文本/图片模型及身份可信范围、新闻/深度数量、预估阅读时长、每条可点击规范来源、警告/阻断、相对上一 revision 的差异，以及收件组名称、快照版本、人数和指纹。
- 编辑预览另展示 AI 审稿结论与仍需确认项、修订轮次、图解状态/跳过原因和流程溯源入口。读者版不展示内部错误、模型调用日志或“待核验”占位稿；有问题的内容留在编辑工作区，不渲染进可批准正文。
- 图片预览使用可在本机直接显示的路径或资源，不要求用户先发送邮件才能检查图片。
- 正式批准前必须通过 HTML、CID、链接、主题、个性化和名单的确定性 preflight。保留测试名单发送能力；模板、CID/个性化逻辑或邮件资产管线变化时必须测试发送，日常内容变化不强制重复测试邮件。
- 测试投递须有对应测试名单的授权；正式发送授权不自动覆盖额外测试收件人。测试未执行必须如实记录，不能将浏览器截图或 SMTP dry-run 标为测试邮件已投递。

#### 11.1.1 最终呈现与多端验收

- 桌面保持适度阅读宽度，手机采用自适应布局；在 320、390、430 像素视口下，邮件正文不能因固定容器、长英文名称或研究图片产生横向溢出、裁切与内容重叠。目录、标签、来源和图文应自然换行，不用整封缩小到难以阅读来掩盖问题。
- 用实际最终 HTML 检查目录数量、锚点、栏目顺序、阅读时长、摘要与正文一致；移除或补入卡片后同步更新，不能保留旧版导语或空栏目。整期 7 条新闻加 1 篇研究仅为 9 月 10 日样本，不设为固定模板配额。
- 标题、事实、价值与启发有清楚层级；减少重复段落和泛泛结论。来源保持可辨识、可点击；截图或 CSS 测试不等于链接与 CID 有效，仍单独执行打包检查。
- 检查原生图及最终压缩图在邮件尺度下的表现，重点看有向关系、分支、数值口径和中文标签。复杂图允许查看原尺寸，但正文必须独立说明核心方法与结果；不能用“大图能看清”豁免手机端主要内容不可读。
- 验收保留桌面/手机截图与视口、实际 HTML/资产 hash、图片加载结果及对应 MIME/CID 检查；代表性真实客户端至少覆盖现用 Foxmail 和一种移动邮件客户端。浏览器通过只是部分证据，不冒充所有邮件客户端已验证。

#### 11.1.2 阅读层级、研究图解与部门能力启发

- 日常版以“重点先行”为设计方向：首屏给出当期真实变化与关键判断，再按重点解读、研究深读、短动态组织内容。重点文章与快讯有明显篇幅差异，目录不替代摘要；具体顺序可随当期价值调整，不强制每期凑齐固定主线或模块。
- 刊头保留期数、日期和内容数量，期数仅显示完整英文格式 `VOLUME 42`，不再并列重复展示“第 42 期”。刊号整行采用统一字号的等宽字体，以适度字重和字距加强识别，不单独放大数字；下方用品牌色短细线与日期分隔，保持白底，不增加填色徽章或重复文案。沿用当期已确定的编号，不因展示样稿、配色切换或重新渲染而重新计数。9 月 10 日样稿应沿用原正式稿的第 42 期，展示为 `VOLUME 42`，不可根据当前预览日期改成另一刊期。
- 保留可点击的“本期导览”：概括当期实际存在的部分，显示栏目名称、数量与一句内容提示，并跳转到对应正文。导览顺序与正文一致，无内容的部分不展示，增删内容后同步更新数量与目标；摘要和导航可以合并呈现，保持白底、紧凑且可扫读。正式邮件使用普通 HTML 锚点链接，不依赖 JavaScript，锚点需唯一且可定位；实际邮件客户端的跳转表现纳入 11.1.1 验收。
- 日常默认纯文字报纸版，无图模式不调用图像 API，不依赖图片可用账号；深度保留核心结论、机制、证据、应用启发、边界和来源。研究图解能力仍保留为显式选择项，启用时继续执行第 10 节完整解析、Handoff、实图审核与 CID 流程。V2 首个影子包只接纯文字呈现；有图分支仍由现有链维护，迁入 V2 前单独验收。
- 复杂图以正文中的可读机制、证据和边界补充；邮件尺度不能让读者只靠缩小图片理解核心内容。正式版需要核对图片实际加载及原尺寸查看入口，禁用假入口或不可访问的本地路径；图片不可用时仍能独立读懂正文。
- 保留“部门能力启发”作为重点稿和深度模块的可选编辑层：结合来源写明可能沉淀的能力、适用角色/场景及判断价值的观察方式。示例包括可回归的评测用例、可修订的流程知识、连续编辑的协作评估。它们是来源启发与待验证应用假设，不写成部门已具备的能力、确定收益或已下达的行动计划。
- 适度保留启发：重点稿与研究模块可展开一段；相关短动态可保留一句工作启发或行业视角，无自然关联时不强行映射具体部门、金融场景或同一能力主线。结构化内容仍按 9.2 保存事实、关注价值、观察与必要边界；紧凑呈现可合并重复句，但不能抹去改变判断的限定信息。
- 基础配色采用贯通白底、统一深灰正文、中灰辅助文字和浅灰细线；品牌识别保持稳定，每日强调色集中用于刊头“AI”、期数、主标题的一处关键词、导航标记及来源链接等位置。栏目、研究与部门能力启发不分别分配不同颜色，不用多彩拼接刊头；主标题允许有限的重点着色，正文不逐句跳色。导读、研究模块与部门能力启发不铺大面积彩色或浅彩色背景；以留白、字重、字号和对齐组织层次。既有科技紫与活力橙样稿保留作对照，不把“减少杂乱”机械等同于全页灰化或一律低饱和；具体观察见 [视觉参考记录](EMAIL_VISUAL_REFERENCES_2026-09-11.md)。研究图按机制语义保留必要颜色，不为匹配邮件主题而重染或修改已审图。
- 每日强调色按刊期日期确定，基准日为 2026-09-10，采用已确认七色：朱砂红 `#A3473F`、梅子紫 `#86536F`、钴蓝 `#4168A2`、灰调亮橙 `#D38243`、灰调鸢尾紫 `#9580C7`、灰调钻石蓝 `#4C9EC1`、灰调蒂芙尼蓝 `#5BAAA4`。草色不进入色池。小号标签和链接使用对应较深 ink 色。颜色、色盘版本必须冻结进当期 revision；同一期重建沿用原色值，不随打开时间或当前配置改变。配置事实源为 `config/newspaper_accent_palette.json`。
- 字体沿用用户确认的报纸版宋体：`Noto Serif SC / Songti SC / STSong / serif`；刊头 AI 保持相同字体，仅为 `1.22em` 并下调 `3px`，不得替换为几何无衬线。中文品牌色保持 `#353A1E`，正文为中性深灰。刊号、日期及编号保留等宽字体回退。远程字体不可用仍须可读，邮件不依赖字体下载。
- 参考 The Neuron 的报纸风格已于 2026-09-14 被确认为默认日常模板：白底、刊头旁导览、重点稿与能力启发、重要补充及短讯，窄屏回到单栏。导览定位完整日报对应位置，无空栏目或隐藏的其他内容。旧方案保留为历史参考；今后调整基于这版逐项修改，不回退到历史样稿默认值。
- 展示样稿的主题切换、字体选择和宽度选择仅用于比较设计，不作为邮件内必需交互。上线前按 11.1、11.1.1 对最终邮件模板、字体回退、图文、链接与 MIME/CID 进行验收，并在已有测试名单授权范围内测试投递；样稿生成不能记作生产模板已接入或客户端已通过。

### 11.2 人工编辑

编辑者应能用结构化操作完成：补入候选、设为必选/移出当期、调整优先级、排除、改栏目、重排、设为/撤下深度、撤图保留正文、重绘图片、补充/替换证据来源、单卡重生成，以及编辑标题、事实摘要、值得关注、工作启发和边界提示。不得再靠一次性临时脚本修改正式稿。

一次编辑会话中的多项修改可在工作草稿中作为一个事务提交；生成新预览时才冻结为新 revision。所有操作记录操作者、原因和前后差异，并重新触发受影响的来源、事实与 HTML 校验。已批准或已发送 release 不得原地修改。

每日运行完成或阻断后，编辑者按固定顺序查看：来源覆盖与运行状态 → 入选/拒选/判重 → 人工补链 → 正文和 AI 审稿问题 → 深度及可选图解 → 最终邮件与差异 → preflight/测试 → 批准 → 正式发送和投递结果。单阶段失败提供单阶段重试。编辑者可以将当日期次标为日级辅助结果 `SKIPPED` 并记录原因；它不进入 revision 主状态链，未发送内容不进入跨期去重。

### 11.3 Release manifest

正式批准时冻结一个 `release_manifest`，至少引用：

- issue 日期、编号、revision 和生成时间；
- 选源结果、证据链与材料包哈希、冻结的采集截止时间及各源实际覆盖/失败记录；下一期的覆盖截止 `C` 从此读取，人工补入单条新闻不能把整期覆盖截止推到该新闻时间；
- 内容 JSON 与 HTML 哈希；
- 实际发布的卡片/事件 ID 与逐条经核对的来源身份、补漏候选引用；只包含最终正文，作为跨期去重与补漏核销的不可变依据；
- 每个执行单元的文本模型调用身份；
- 深度呈现/无图原因、图解 manifest 与最终资产哈希（如有）；
- 不可变 `recipient_snapshot_id`、收件名单版本、规范化去重规则、人数和指纹；
- 基础 HTML 哈希、逐人 MIME/Message-ID 引用及最终发送包哈希；
- preflight/测试结果、正文审稿与实际图片审核的目标 hash、问题处理/人工替代审核记录、批准人和批准时间；
- 代码发布版本、Git commit、发布包 SHA-256、依赖/运行时版本、Schema 版本、配置版本和生效 systemd unit 哈希。

批准与冻结 release manifest 必须是一个事务操作，并对 `issue_date` 设置“当前有效、尚未发送 approved release”唯一约束。任何收件人进入发送中状态后，该 release 不得撤销、替换或修改。

### 11.4 唯一发送入口

- 正式发送器只接受服务器上的 `release_id`，重新校验批准状态、manifest/资产哈希、名单快照和原子发送 claim；拒绝任意 HTML/EML/path/收件人覆盖参数。
- 只有独立 publisher 服务身份可以读取 SMTP 凭据；制作、预览、本机/Codex 和反馈服务均不可读。低层 SMTP 脚本不得单独持有生产凭据。
- 同一日期默认禁止第二次正式发送。失败收件人的续传引用原 release；内容或名单纠错重发必须创建带 `reissue_of` 和原因的新 release，重新预览、preflight 和批准。
- 发送前原子创建唯一 `(release_id, recipient_id)` intent；逐人至少记录 `READY / IN_FLIGHT / ACCEPTED / REFUSED / UNKNOWN`，期级记录 `SENDING / PARTIAL / SEND_UNCERTAIN / SENT`。
- 只有明确未被 SMTP 接受的 `REFUSED` 可自动续传；断线等 `UNKNOWN` 不得自动重试，必须先核对 SMTP/provider 记录或人工确认。固定 Message-ID、MIME hash 和 attempt ID 用于核对，但 Message-ID 本身不被当作幂等保证。
- 邮件使用 `AI DAILY` 作为显示名，图片以 CID 内嵌并兼容 Foxmail。
- 周聚合键按 `(ISO year, ISO week, recipient_id)` 维护；每名收件人当周第一封成功邮件成为自己的会话根。

## 12. 反馈需求

### 12.1 原文可访问性优先

- 邮件标题和“来源”默认直接链接到规范原文 URL，不经过 Vercel 或其他统计域名。评分、评论和估算打开独立工作，不作为打开新闻的前置步骤。
- 邮件客户端不支持可靠的 JavaScript/后台 beacon；不得承诺同时实现“原文直达”和“无损逐人点击统计”。使用直链的 release 将来源点击记录为 `not_collected`（未采集），不显示为 0 次或 0% 点击率，也不用像素打开量推算来源点击。
- 网站预览若支持脚本，可以在不拦截正常导航的前提下尽力上报点击；失败直接放弃。该指标单列为网页预览点击，不能混为邮件点击或用来保证全部用户已阅读。
- 旧 `/click` 跳转接口仅作历史邮件兼容：请求到达后统计存储失败不应阻止合法跳转；但 DNS/TLS 连接失败发生在处理程序之前，“异步记日志后 302”无法解决这类错误。
- 评分/评论页面仍受反馈站点网络可达性限制；打开失败不能显示提交成功。已发送邮件中的链接不能远程替换，新增直链策略只对之后生成并发送的邮件生效。

### 12.2 统计与补偿

- 每名收件人使用匿名反馈 token，不在公开链接中暴露邮箱。
- 打开估算、有效点击、评分、评论和参与率必须区分统计口径；release 记录来源链接模式及是否启用点击采集，直链期次按 12.1 显示未采集，不能与历史追踪期次直接比较 CTR。
- 收件人数/投递分母来自正式 release 中 SMTP `ACCEPTED` 的逐人记录；`REFUSED / UNKNOWN` 单列。`ACCEPTED/SENT` 只表示 SMTP relay 接受，不等于最终进入收件箱。
- 反馈同步以 `(release_id, recipient_id)` 幂等 upsert，写入持久重试队列；同步失败不得把已发送邮件标记为失败。
- 配置中只保留一个明确的反馈启用开关，环境变量不能暗中覆盖“关闭”语义。
- 生产继续使用 Vercel + Supabase；本地 SQLite 仅用于开发与诊断，不作为双重事实源。
- 反馈 token 绑定 release/recipient scope，支持过期和密钥版本；日志和代理不得记录完整 token。
- 发送后可记录 `manual_promotions / auto_selected_drops / missed_high_value / false_duplicate / scoring_feedback`。只有编辑者确认的复盘样本进入黄金回放集，且不得自动修改评分权重。

## 13. 调度、部署与可观测性

- 服务器工作日 08:30 触发制作；时区固定为 `Asia/Shanghai`。
- 系统在预览就绪或运行阻断时通知编辑者，并记录预览就绪耗时；完成时间目标在影子运行后基于真实数据设定，不先用硬截止时间增加失败率。
- 自动发布 timer 默认禁用。启用限时自动模式时，发布策略必须包含开始/结束日期，并在到期后自动恢复人工审核。
- 每次运行记录代码版本、配置版本、模型/provider、阶段耗时、重试、失败原因和最终 revision。
- 保留现有逐卡 checkpoint、主备图片线路、压缩/CID、来源直链和逐人发送记录，将其收敛到统一产物与预算，不各建一套相互覆盖的状态文件。
- 记录分阶段耗时、模型调用量/成本（不可得时标未知）、缓存命中、返工原因、弃稿、无图原因及人工改稿；按 P50/P95 比较影子期基线，分别衡量速度、事实/分类质量与可用性，不能只统计“生成了 HTML”。
- 部署来自版本化发布包；systemd 实际生效内容必须纳入部署验收，不以仓库中的模板文件代替。
- systemd 验收至少检查生效时区、`Persistent` 补跑语义、timer/手工防重入、专用非 root 用户、只读版本包、凭据隔离和未启动/失败告警。补跑只允许在同一工作日截止时间前补制作，绝不补自动发送。
- 服务器事务账本是批准、release 和 send intent 的事实源；SMTP 响应是“relay 是否接受”的事实；Supabase 是反馈事实；本机只同步预览和审核所需的最小副本，服务器不可用时默认停止正式发布。
- 失败原因必须转化为下一步动作，例如“重试该卡片”“选择下一研究”“重新授权模型”，而非只返回堆栈。
- 编辑视图提供采集 → 候选 → 入选 → 成稿 → 正式发布的数量与逐条去向；单列新发现缺口、评分/资格未入选、生成失败、已选未发布、待审积压及最老等待时长。人工报告的漏项作为已知样本统计，不拿它估计全网召回率。
- 补漏成效以“重审后实际发布”和“明确合并/放弃”计数，草稿恢复单列；源无响应、解析为零和信号匹配为零不能合并为“没有高价值内容”。发布后队列同步失败写待补算告警，不改变邮件投递结果。
- 账本、release manifest、资产、名单快照、配置版本和生效 unit 必须定期备份并做恢复验证；恢复后仍须保留 `ACCEPTED/UNKNOWN` 防重事实。

## 14. 质量门与复杂度预算

### 14.1 三档规则

| 类型 | 处理方式 | 典型规则 |
| --- | --- | --- |
| 硬阻断 | 不可批准/发送，可先修复或移除受影响的普通项 | 0 条新闻；正式 revision 中仍有未完成 AI 编辑的条目；人工必选条目失败；无可核对证据或高风险事实越界；确认重复事件；拟发送资产血缘不一致/事实错误/未完成实际审核；正文既无有效 AI 审核也无有效人工替代；名单未冻结；revision 未批准；未经授权重复发送 |
| 自动修复 | 修复后继续 | URL 规范化、危险控制字符清理、CID/文件名编码、无语义损失的图片格式/压缩处理，以及按错误类型执行的单源抓取或单卡有限重试 |
| 软警告 | 生成预览，交给审核 | 1–4 条新闻、栏目不均、阅读时间偏长、可信二手来源、标题偏长/英文比例、一般边界提示不足、深读价值临界、图片信息密度一般但事实无误、技术故障导致无图 |

### 14.2 约束复杂度预算

- 能由代码确定的规则不得再写进模型 Prompt。
- 一个字段只有一个事实来源；栏目、模型、反馈开关和 provider 不得在多处分别定义。
- Prompt 不设置机械栏目配额、精确句数或逐项关键词命中要求。
- Handoff 简化、原生/混合路线与总预算必须用同一组输入对比；没有效果数据前不继续增加字段、颜色禁令、强制图像密度或更多审核角色。
- 新增硬阻断必须同时说明：防止的具体损失、为何不能自动修复、对应测试；否则默认作为软警告。
- 不因一个可丢弃的候选失败而让整期制作失败。
- 不用更多 Prompt 规则修补可由路由、Schema 或来源解析解决的问题。
- 图片技术不可用不是正文事实失败；图片质量不合格只禁止使用该图。按规则撤下后不要求不存在的图片提供审核文件，避免“允许无图”却被旧研究图门禁再次阻断。
- 每项问题同时注明影响范围（候选/卡片/图片/整期/发送）与恢复动作；确定性硬问题不能被 AI 高分豁免，AI 的一般偏好也不能直接升级为代码硬门。

## 15. 失败处理

| 故障 | V2 行为 |
| --- | --- |
| 单个自动源不可用 | 记录源健康度，继续其他来源 |
| 人工链接不可抓取 | 保留候选和错误，允许补充一手材料；不得无证据扩写 |
| 单条普通新闻生成失败 | 按错误类型有限重试，仍失败则标为本次 `DROPPED`；保留其他成功卡片并继续预览，符合条件的候选进入跨日补漏 |
| 高价值项因来源封顶或预算未入选 | 保留原始分、有效分和原因，进入来源待审/待复核；不能为补漏自动解除证据门槛 |
| 补漏候选达到 7 天或当次 12 条预算 | 到期转待审，预算外保留未复核；不删除历史、不冒充已发布、不绕过正常选稿上限 |
| 人工标记必选新闻生成失败 | 阻断批准，等待人工补救 |
| 最终 0 条新闻 | 阻断批准和发送 |
| 深度抓取失败 | 依次尝试下一合格候选，最多 3 个；耗尽后转纯新闻版 |
| 草稿审核要求修订 | 至多 2 轮定向修订复核；普通问题项仍失败则退出，必选/全稿共性硬问题阻断批准 |
| 草稿审核不可用 | 保留待审预览，可人工替代审核；不得伪装 AI 通过，限时自动模式不发送 |
| 图解质量不合格 | 至多一次定向修复且计入图片总预算；仍失败撤下图并保留合格深度文本，待人工审阅 |
| 主文本模型不可用 | 停止正式稿，不静默降级 |
| 图片 provider 技术不可用 | 在冻结的主备计划及总预算内处理；都不可用时无图版继续审稿/终检，记录跳过原因；不自动换未批准线路 |
| 图像流程记录不可验证/视觉审核不可用 | 不采用未核验图片；标准模式可按规则人工核实导入或撤图，限时自动模式停止发送 |
| HTML/CID 校验失败 | 阻断发布，保留可诊断产物 |
| SMTP 明确拒收 | 保留逐人状态，仅续传 `REFUSED` 收件人 |
| SMTP 接受状态不确定 | 标为 `UNKNOWN/SEND_UNCERTAIN`，停止自动重试，先核对 provider 或人工确认 |
| 邮件已接受但总账提交失败 | 从事务 send intent 与逐人状态恢复；无法判断时进入 `UNKNOWN`，禁止盲目重投 |
| 邮件已接受但补漏视图更新失败 | 邮件保持发送事实，依据不可变实际发布快照重建派生视图，不重发邮件 |
| 反馈同步失败 | 邮件保持 `SENT`，反馈任务异步重试 |

## 16. 安全与数据边界

- API Key、SMTP 密码和数据库密钥只存在于受控环境变量或秘密存储，不写入代码、Prompt、日志、release manifest 或审核包。
- 第三方文本/图片网关按阶段列出允许外发字段、保留/训练政策和失败回退方式，并经管理员批准；禁止外发密钥、邮箱/反馈 token、评论、内部 URL/路径、日志和带认证查询参数的 URL。审计只记录 provider/request ID 和载荷哈希，不保留秘密。
- 抓取器在首次请求和每次重定向后都校验协议、DNS 与 IPv4/IPv6 地址，阻止 loopback、private、link-local 和云元数据网段，并限制跳转、响应体、超时，防止 SSRF 与 DNS rebinding。
- 收件名单属于敏感数据；预览和审核包只显示数量、版本和指纹，不默认复制完整地址。
- 正式发送、重发、自动发布策略和 provider 变更必须可审计。
- 本机/Codex 导入包由服务器重新计算哈希并校验 Schema、MIME、尺寸和路径；拒绝绝对路径、`..`、symlink、可执行文件和超限包。只能自报的 provider 血缘标为 `self_reported`，不得进入无人值守自动发布。
- 审稿/生图只接收已批准外发的数据；调用记录仅导出相关最小片段并去除凭据，不复制完整 Codex 对话或机器配置。Prompt 存在受控审计包中，不含秘密；UI 日志默认只展示 hash 和安全摘要。

## 17. 最小产物契约

每期只规定五类核心产物，其他均为实现细节：

1. `candidate_pool`：候选及来源、事件、抓取和人工操作记录；包含未发布补漏状态、延期/放弃原因及发布引用，补漏队列只是其派生视图；
2. `selection_revision`：本次入选、拒选、排序和深度候选；
3. `content_revision`：AI 编辑结果、内容呈现形式、模型调用身份、审稿/定向修订记录、深度 brief 与 handoff 引用、无图状态及原因；
4. `asset_manifest`：有选用图片时必需，记录输入到最终图的血缘和实际审核；无图时不要求伪造空的通过记录，失败 attempt 仍保存在运行账本；
5. `release_manifest`：冻结后的正式内容、名单、审批和发送引用。

这些产物必须有 Schema 版本和不可变 ID。文件名可以调整，但不能再依赖约定文件名推断正式状态。草稿 attempt/审核快照、调用执行记录与派生步骤是已有对象的附属记录，不增加第六套顶层事实源。历史 `paper/research` 字段通过一次迁移映射到深度内容；兼容读取期间不双写两套互相独立的正文或图片路径。

## 18. 验收标准

### 18.1 回放验收

使用至少 20 个历史工作日及已知错误样本回放，覆盖：

- 模型收入/成本新闻不得误入模型更新；
- 教程、搜索入口变化、硬件标准不得误判为模型发布；
- 聚合早报优先解析一手来源；
- 断档最长 96 小时补漏和跨期去重；
- 周五选源截止与发送之间、周五下午/晚间以及 RSS 滚动裁剪的覆盖缺口；发布时间、发现时间、实质更新时间不能混用；
- 工程方法无需越过重大事件统一分数门槛，三轨不增加展示栏目、不强制配额；
- 深度抓取失败后换候选或生成纯新闻版；工程方法可以进入深度但不冒充实验研究，也不与新闻重复；
- GitHub/网页原文、Prompt 和占位内容不可进入正式邮件；
- 单条普通新闻失败不会拖垮其余内容；
- 周一漏发后当周后续邮件仍可聚合；
- 本机/Codex 资产能导入且不能绕过批准门；
- 标注为必选的高价值事件在候选池和最终选源中的召回结果可解释。

### 18.2 可靠性验收

- 同一日期存在多个 revision 时，系统能唯一指出批准版和已发送版；
- 正式发送可以从 release manifest 唯一还原选源、文本、图片、名单、版本和审批；
- 同一收件人不会因并发启动、崩溃恢复或重试重复收到同一期；
- 文本/图片调用记录 requested/returned 身份及身份来源；与响应或实际命中的 approved endpoint registry 一致，不能由调用方默认配置伪造；
- 反馈同步失败不影响发送状态，并可独立重试；
- 阻断反馈域名 DNS/TLS 后，邮件来源仍可直达原站（前提是原站可用）；直链 release 的点击指标显示未采集，网页预览统计失败不拦截导航；历史跳转链接仍有网络依赖，不伪报已修复；
- 08:30 定时单元、实际 systemd 配置和部署版本一致；
- 生产密钥不出现在仓库、产物或普通日志中；
- 故障注入必须验证：普通单卡超时/Schema 错误不阻断其他卡且不重生成成功卡；图片 provider 故障保留合格深度正文并产出无图预览；两个发布进程只能有一个取得 claim；SMTP DATA 前后断线与落账前终止不会触发盲目重投；V2 部分投递后回退 V1 不会重复投递；反馈重复同步保持幂等。
- 影子期记录按截止时间产出预览率、卡片首调/重试后成功率、普通卡丢弃率、图像服务成功率、图片质量通过率和无图预览率；主动不配图、技术不可用、质量失败分别计数，不能靠跳图把生图成功率做高。先建立基线，再决定 SLO，不用未经验证的百分比直接阻断生产。

### 18.3 编辑质量验收

- 每条正式新闻都有可核对来源、中文事实摘要和明确价值说明；
- 关键事实不超出材料证据；高风险信息满足最低证据要求；
- 新闻目标 5–10、硬上限 12，低于目标时不以低价值内容填充；
- 选用图解的主机制、证据、范围和中文标签可读，且与深度文本一致；无图版同样能独立理解，不含图片占位或悬空图注；
- 与 V1 的标注样本相比，人工删除、改栏目和纠错次数不增加。

验收拆分为历史原因还原、队列状态与幂等测试、真实来源适配器回放、最终 HTML/资产检查、获授权的客户端投递验证；分别记录通过与未覆盖项。比较召回质量、误选/重复、编辑耗时与读者可读性，不以“今日补了 8 条”或单次 HTML 成功替代完整验收。

## 19. 迁移顺序

V2 不一次性重写全部实现，按以下顺序降低风险：

1. **冻结需求与黄金样本**：确定本文、历史回放集和不可丢失行为；
2. **先统一事实与发布门**：引入 revision/release manifest、唯一发送入口、只以已发送内容去重；
3. **再统一配置与路由**：消除 Prompt、Python、JSON、环境变量之间的多重事实源；将三轨资格、统一覆盖窗口、事件归并作为同一选源模块实现，先回放 18.4 样本再进入影子运行；
4. **迁移生成链**：逐条编辑与局部 checkpoint；独立审稿先只报告建议，通过回放后启用最多两轮返工；深度可选，工程/方法可参与但不增加配额；
5. **迁移图片和反馈**：六字段 handoff 编译器、受控调用记录、实图审核与最终资产绑定一起迁移；保留认可的原生路线，加入无图深度降级，复核自动模式边界；统一 CID 与异步反馈补偿；
6. **并行影子运行**：V1 与 V2 同时制作但只发送 V1，V2 不持有生产 SMTP 凭据，只允许打包或发测试名单，比较 5–10 个工作日；
7. **人工切换**：先冻结发送，停用并确认 V1 无运行进程，备份账本/配置/生效 unit，再启用 V2 并验证；V1/V2 迁移期共用同一发送事实或完整导入 `ACCEPTED/UNKNOWN`；
8. **安全回退**：先停用 V2，再恢复 V1 代码，但继续使用同一发送账本，绝不恢复一个不知道 V2 已投递记录的旧账本。
