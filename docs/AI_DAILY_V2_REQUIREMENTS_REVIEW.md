# AI 日报 V2 需求多轮评审记录

> 评审对象：[AI_DAILY_V2_REQUIREMENTS.md](./AI_DAILY_V2_REQUIREMENTS.md)  
> 评审目标：发现遗漏、冲突、过度约束和生产风险，并将可确定的修复直接吸收到主需求。  
> 原则：评审不是继续堆规则；优先删除重复事实源、缩短主链、把软偏好从硬阻断中移出。

> 版本说明：0–7 节保留 2026-08-31 的基线评审；第 8 节记录 2026-09-07 修订，第 9 节记录 2026-09-08 修订，第 10 节记录 2026-09-10 修订，当前主需求版本为 1.3。历史章节中的“研究有正文就必须有图”“精确中文默认混合”“图片失败不能保留深度文本”等取舍已被主需求 1.2 第 10 节替代，1.3继续保留该调整，不再以历史取舍作为实施依据。文档评审完成不代表生产实现或回放验收完成。

## 0. 现状审计：从已有系统提取真实需求

### 主要发现

1. **日期和重生成版本混用**：同一天存在自动版、人工版、Codex 版和最终发送版，但旧状态只表达一个 run，可能出现“状态失败、邮件已发”。
2. **正式发送入口不唯一**：低层 SMTP 脚本可直接发送任意 EML，候选稿可能绕过质量门。
3. **生产实现不可复现**：本机、服务器、仓库模板与 systemd 实际配置存在漂移，且大量生产代码未形成稳定版本基线。
4. **未发送草稿污染去重**：旧代码会读取近期生成稿，导致只预览未发布的新闻以后被误认为已发。
5. **配置事实源过多**：栏目、模型、图片线路和反馈开关同时分散在 JSON、Prompt、Python、环境变量和 systemd 参数中。
6. **研究有填空倾向**：部分 fallback 逻辑倾向选择擦线论文，与“研究不是每天必有”冲突。
7. **反馈缺失与发送失败混淆**：后台分母同步是独立问题，不应改变邮件投递事实。

### 已回写的修复

- 新增 `issue_date → revisions → approved release` 对象关系；
- 规定 revision 不覆盖、正式发送绑定 release manifest；
- 规定唯一正式发送入口；
- 跨期去重只读取正式已发送 revision；
- 研究明确为 0–1，候选耗尽后生成纯新闻版；
- 服务器作为生产事实源，本机/Codex 只能经过统一导入与发布门；
- 反馈同步成为发送后的独立状态；
- 运行记录绑定代码、配置和实际 systemd 版本。

## 1. 第一轮：业务完整性与编辑目标

### 评审问题

#### 1.1 “新闻够不够多”与“不凑数”存在冲突

如果把最低 5 条设为制作硬门，低新闻日会直接失败；若完全没有目标，又容易出现内容过少。

**修复：**定义目标 5–10 条、硬上限 12。0 条生成阻断预览且不可批准；1–4 条生成警告预览，标准模式显式确认后可批准，限时自动模式不发送；不降低选源线。

#### 1.2 栏目重叠会继续制造误分类

旧结构中“产品发布”和“产品/分发入口”边界高度重叠，而“模型更新”又容易吸入模型商业新闻。

**修复：**合并为“产品与入口”，最终为 1 个可选研究板块加 5 个新闻板块；同时给“模型更新”一个事件定义，而不是关键词定义。

#### 1.3 人工补入新闻不是异常，而是稳定需求

历史上大量高价值内容来自用户补链，但旧流程常靠临时脚本插入。

**修复：**把人工链接、升降级、排除、改栏目和重排纳入统一候选池与 revision 审计。

#### 1.4 “没有研究”与“研究制作失败”需要区分

二者对发布行为不同：前者可正常发布，后者若仍保留研究正文却缺图则不完整。

**修复：**无合格研究直接走纯新闻版；含研究 revision 的图片失败则阻断，人工移除研究后产生新 revision。

#### 1.5 周邮件聚合不应依赖周一

周一节假日、制作失败或未发布时，后续邮件仍应形成一个会话。

**修复：**当周第一封成功邮件成为根；聚合键包含 ISO 年份和周次。

### 本轮取舍

- 没有增加“每天必须覆盖每个栏目”；栏目均衡只是软偏好。
- 没有规定每条摘要的精确字数；只定义必需语义字段。
- 没有为每类新闻创建不同流水线；仍走一条新闻编辑主链。

## 2. 第二轮：生成可靠性与约束复杂度

### 评审问题

#### 2.1 单条模型失败不应拖垮整期

旧自动门曾要求所有卡片一次完整成功，任何一条失败都会让已有高质量内容失效。

**修复：**新闻逐条调用，默认最多一次重试；普通候选仍失败则退出当期，必选重大事件失败才阻断批准。

#### 2.2 不能用静默降级换成功率

切换到较弱文本模型或模板稿虽然能产出文件，但会造成摘要短、分类错、原文泄露等隐性质量问题。

**修复：**生产主模型固定为 `gpt-5.6-sol`，不可用时停止正式稿；备选模型必须独立验收并显式展示。

#### 2.3 规则重复写入 Prompt 会相互矛盾

日期、URL、分类、来源、字数、图片风格和失败策略在多个 Prompt 与脚本重复出现，既增加 token，也让模型难以抓住主任务。

**修复：**按职责分离：确定性事实交给代码，模型只做语义编辑；新闻卡片仅保留 5 个内容字段加一个栏目建议。

#### 2.4 图像约束越写越长，仍可能出现错字和过强结论

“禁止盾牌”“必须高清”“先背景后文字”等零散补丁不能替代稳定 handoff 和确定性排版。

**修复：**研究图只保留主机制、关键证据、范围提示与最多两条结果线索；使用短结构化 Visual Handoff。关键文字不稳定时切换混合渲染，不继续扩写 Prompt。

#### 2.5 provider 标签可能与实际调用不一致

调用方默认 provider 曾把 Marshall 产物标成另一条 Image2 线路，导致血缘不可信。

**修复：**记录 requested model 及响应返回的 model/provider；若响应不返回 provider，则使用实际请求命中的不可变 endpoint registry 项，并标记身份来源为 `registry`。不接受调用方随意默认，也不把 requested model 冒充 returned model。

### 本轮删减或降级的约束

| 旧倾向 | V2 处理 |
| --- | --- |
| 1–4 条新闻即整个 prepare 失败 | 改为预览警告；0 条仍阻断；不凑数 |
| 每个栏目要有内容 | 删除 |
| 研究每天必须有 | 删除 |
| 每条严格字数/句数 | 删除，改为语义字段 |
| 栏目配额影响发布 | 降为软偏好 |
| 单条普通卡失败阻断整期 | 改为有限重试后退出该条 |
| 大量负面词堆入生图 Prompt | 改为短 handoff + 审核/混合渲染 |
| 任何反馈同步错误视为发布失败 | 改为异步补偿 |

## 3. 第三轮：运行、安全与可恢复性

### 评审问题

#### 3.1 发送事实与账本提交不是原子动作

SMTP 已投递但总账写入失败时，可能发生系统误判和重复发送。

**修复：**逐人投递状态优先记录并可恢复；总账从投递事实重建；正式发送入口执行幂等检查。

#### 3.2 正式发送必须可完整还原

旧 send ledger 没有完整绑定选源、材料、Prompt、图片及审核 revision。

**修复：**release manifest 冻结内容、资产、名单、模型、代码、配置和审批引用；发送器只读取它。

#### 3.3 密钥与外发数据边界不清晰

第三方模型网关会接收新闻材料或研究内容，若未明确批准会形成数据治理风险。

**修复：**密钥不进入仓库与产物；provider 需管理员批准并列明最小外发字段；正式 manifest 只记录身份和哈希，不记录秘密。

#### 3.4 定时模板与实际 systemd 可能漂移

检查仓库文件不能证明服务器实际运行的参数一致。

**修复：**部署验收读取实际生效单元；每次运行绑定 release version、Git commit 和配置版本。

#### 3.5 自动发布有被临时脚本永久遗留的风险

为请假等场景复制一套自动发布脚本会产生两条逐渐分叉的生产链。

**修复：**只保留一个发布实现；免审核是带起止日期的策略，到期自动回到人工审核。

### 残余风险

- 邮件协议无法提供真正的跨 SMTP 原子事务，只能依赖逐人幂等状态和恢复机制降低风险。
- 外部网页和模型网关本身会波动，V2 能隔离单源/单条失败，但不能保证每天都有同等数量的高价值信息。
- 图像模型对中文文字的稳定性仍有限，因此混合渲染是必要兜底，而不是更多 Prompt 可以彻底解决的问题。

## 4. 第四轮：反向简化审查

本轮不再问“还缺什么规则”，而是逐项检查能否删除。

### 保留为硬阻断的条件

只保留会导致以下实际损失的规则：

- 错误或无证据内容被发送；
- 未经 AI 编辑的原文、Prompt、占位稿被发送；
- 重复事件或重复邮件；
- 文本/图片/名单/审批血缘不一致；
- 含研究的邮件缺图或图片存在事实错误；
- 未批准 revision 或未冻结名单被发送。

### 明确不是硬阻断的条件

- 新闻为 1–4 条（0 条仍是硬阻断）；
- 某栏目为空；
- 阅读时长偏长；
- 来源分布不够均衡；
- 图片美感或信息密度一般但事实正确；
- 研究候选不足；
- 反馈后台暂时缺少分母。

### 最终复杂度结论

V2 主链保持 7 个主状态、5 类核心产物、1 个正式发送入口、1 套栏目事实源和 3 档质量规则。其他能力通过候选元数据、软警告或辅助任务表达，不再增加平行工作流。

## 5. 三路独立复审后的二次修订

初稿完成后又分别进行了产品完整性、生成可靠性、运行/安全三路只读审核。本轮只吸收会造成误发、漏发、错误版本或整期失败的意见，没有把所有建议都转成新流程。

### 5.1 产品完整性复审

发现并修复：

- 明确定义新闻数不含研究，0 条不可发，1–4 条只可人工确认，11–12 条显示阅读警告；
- 将“六个板块”澄清为一个可选研究模块加五个互斥新闻栏目，空栏目不显示、同一事件不重复；
- 补全人工补链的返回状态、`must_include` 边界和批准失效规则；
- 增加标题/摘要/来源/边界编辑、单卡重生成及 revision 差异；
- 预览改为同一发送内容、模板、最终资产和名单快照，补上 preflight 与按变更触发的测试发送；
- 将固定“周一补漏”改为按上次成功发送时间触发断档审计；
- 保留今日编辑简评、今日小结与 10 分钟软阅读预算。

### 5.2 生成可靠性复审

发现并修复：

- “未完成 AI 编辑”只阻断仍保留在正式 revision 的条目或人工必选条目；普通失败条目标为 `DROPPED`；
- 每条卡片有独立 attempt/checkpoint，重试不得重生成已成功条目；
- 重试按超时/限流/Schema/输入错误分类，而不是机械重复调用；
- Schema 只校验传输契约，标题长度、英文比例和一般措辞降为软检查；
- 研究图失败只阻断含研究 revision，同时可生成纯新闻候选版，但不会在自动模式中静默切换；
- 研究的证据锚点扩展为实验、指标、证明、消融或案例，图解适配度降为排序偏好；
- 精确中文/数字默认使用“底图 + 确定性文字叠加”，批准对象是压缩后的最终发送字节。

### 5.3 运行与安全复审

发现并修复：

- 批准、发送 claim 和逐人 intent 需要单机事务与唯一约束，无需引入分布式平台；
- SMTP 增加 `UNKNOWN/SEND_UNCERTAIN`，不再对接受状态不确定的收件人盲目重试；
- 正式 publisher 只接受 `release_id`，且只有其服务身份能读取 SMTP 凭据；
- release manifest 补全名单快照、逐人 MIME 引用、发布包/运行时/systemd 哈希；
- 明确服务器账本、SMTP 接受响应和 Supabase 反馈各自的事实边界；
- 影子 V2 不持有生产凭据，切换/回退始终共用同一发送事实；
- 外部网关最小外发字段、本机导入校验、SSRF 重定向校验和反馈幂等队列进入需求。

### 5.4 有意没有采纳为新硬门的建议

- 没有设定未经影子数据验证的固定 95%/99% SLO，先记录指标再定阈值；
- 没有把每次文字修订、每次模型 attempt 都做成独立 revision；
- 没有增加完整 CMS、消息队列、分布式锁或新运营后台；
- 没有把白底、栏目均衡、标题长度、精确字数和图片信息密度都写成模型 Prompt 硬约束。白底保留为产品视觉主题，并优先由确定性画布保证；
- 没有允许自动模式在研究图失败后静默删除研究并发送。

## 6. 待实现时重点验证的风险

以下不是继续扩写需求，而是实现阶段的验证任务：

1. 旧 run/date 文件如何无损迁移为 revision；
2. 发送中断时逐人状态的落盘时机；
3. 模型网关是否稳定返回实际模型/provider 身份；
4. 历史 20–30 期回放集是否覆盖用户已指出的分类和漏选问题；
5. 服务器与本机的发布包、配置和 systemd 是否能生成同一版本指纹；
6. Codex 兜底图导入后是否与服务器图走完全相同的资产审核门。

## 7. 评审结论

需求已经从“在旧脚本上继续补规则”收敛为：

- 用 revision 与 release manifest 解决状态、重生成和审计问题；
- 用唯一发布入口解决绕过门禁与重复发送问题；
- 用候选池和来源等级解决人工补链、聚合源与一手源问题；
- 用逐条生成、有限重试和可丢弃普通候选提高稳定性；
- 用研究可选、短 Visual Handoff 和混合排版降低图像失败率；
- 用三档规则阻止软偏好继续膨胀为硬约束。

最终矛盾复核未发现阻断项，当前需求基线可以冻结并进入“黄金样本冻结与技术方案设计”阶段，但不应直接一次性替换生产链。

## 8. 2026-09-07：工程方法漏选与周末补漏增量复核

本轮由同一编辑者分三轮复核需求，不宣称为独立多智能体审核。范围为需求、取舍和回放用例；没有修改或部署生产选源代码。

### 8.1 实际输入与问题证据

- 服务器 9/7 正式选源窗口：常规新闻从 9/5 08:30 开始；断档审计标记从 9/4 10:32 上次发送开始，但只接收特定模型/安全事件且新闻分至少 86。
- 原始 AIHot feed 包含周五午后/夜间消息，BestBlogs 包含 9/4 17:20 的 AgentCore 生命周期文章；正式评分候选没有 9/4 条目。此处“时间”是源提供的条目时间，不能直接等同于一手发布时刻。
- 临时扩大窗口的对照结果：AgentCore 旧分 68.5、Microsoft Foundry 上线 Astra 旧分 79.8；分数不足以解释它们的实际工程价值和企业使用增量。
- 当日成稿五张新闻卡中，三张属于同一 OpenAI Wiki 事件及回应。候选被分到不同主题，未实现事件级合并。
- 来源直链已用于现有邮件打包，但本地主 PRD 尚未写明其点击统计代价，旧反馈专项设计仍描述全部经过 `/click`。此次统一进主需求 12.1；旧专项设计的矛盾项不作为 V2 实施依据。

上述是生产与采集快照诊断。新窗口/新轨道的效果仍需按主需求 18.4 回放，不能用诊断模拟替代 V2 实现测试。

### 8.2 第一轮：产品价值与分类边界

| 初步建议中的风险 | 本次收敛 |
| --- | --- |
| 只降低综合分，会连低价值文章一起放进来 | 按时效动态、工程方法、研究前沿判断资格；评分留作轨内排序 |
| 工程轨道等同新增栏目 | 内部轨道与既有六个展示板块分离；AgentCore 通常归智能体工程 |
| 要求架构/代码等至少两种，可能误杀完整方法文 | 用“足以理解并复用/评估的方法材料”判断，列举证据形式而不做机械数量检查 |
| 有代码、有结构图就要求研究图 | 工程文章默认新闻卡；是否深读按研究准入单独判断，同一内容只占一次名额 |
| 官方出处自动等同效果可靠 | 出处与效果主张分别判断，厂商案例保留适用边界；对争议事件保留多源证据 |
| 动态 3–8、工程最多 2 被写成硬配额 | 工程 0–2 只是软偏好，编辑可有理由调整；保留原新闻上限，不加最低动态数 |

结论：用户认可的 AgentCore 作为工程方法正向样本，而不是把 AWS 或这篇文章加入免审白名单。它能进入复核并获得公平比较，也不要求每天必须找到同类文章。

### 8.3 第二轮：补漏完整性与事件增量

- **选源与发送的间隙**：以发送时刻作为回看起点会漏掉周五 08:30 选源后、10:32 发信前的消息；改用已发 release 的覆盖截止，并通过跨期去重处理重叠。
- **跨源执行不一致**：AIHot 有补漏分支，BestBlogs/官方新闻仍可能按 48 小时直接退出；需求要求所有来源采用同一轨道窗口。
- **发布时间与发现时间混淆**：保留各自字段；旧文章新收录不伪装成新发布，延迟发现和日期不明确条目进入待复核。
- **滚动 RSS 的物理缺口**：扩大时间参数不代表源仍保留全部历史。优先现有候选、历史入口或一手列表有界补抓；不足就显示覆盖不全，长假超过 96 小时明确未覆盖范围。
- **事件去重与增量冲突**：Wiki 多源报道合并；同模型的新开放渠道可按新增事实保留。疑似重复不能直接硬删，已确认重复不能各占一张卡。
- **审计记录不完整**：超窗/资格失败等评分前退出也记录原因，避免只看到“候选不存在”却无法定位。

结论：取消统一 86 分的断档入口，同时维持证据和内容价值要求；不会把完整周末列表直接塞入正刊。

### 8.4 第三轮：生成成功率、反馈可用性与简化

- 三轨复用同一候选对象与编辑链，不各建一套服务、模型、定时器或状态机。
- AI 复核有界，默认每轨前 5 个事件及人工必选项；一般一轮，修订仅查受影响项。其预算用尽不是发布硬门，未覆盖部分显式留候选。
- 普通候选复核失败进入警告/待人工判断，已成功生成的新闻继续预览；限时自动模式丢弃需人工确认的普通项，保留原有低条数和必选阻断行为。
- 邮件原文用直链；不承诺在 Foxmail 中运行后台脚本，也不将未采集的点击显示为零。网页预览的尽力上报单列统计。
- 历史跳转接口的数据库失败可与跳转解耦，但到达站点前的 DNS/TLS 失败无法由 302 或异步记日志解决；旧邮件链接不会因后端或新模板改动被替换。

本轮没有增加硬配额、每条评分长报告、必须调用新模型的独立门禁或额外图解要求。保留原有状态链、五类核心产物与发送入口；新增判断放进已有候选/选源记录。

### 9.4 第二轮：流程可信与图像质量

- **规则被使用不等于声明使用**：记录解析/编译版本、输入快照和实际 Prompt 关联；服务器不必运行桌面 skill 文件，但须实现同一契约，并用相同黄金输入回放验证。
- **hash 不等于执行证明**：保留 hash 校验，但增加请求前后受控记录与权限隔离。新图不能靠改文件名、时间戳、schema、policy 或 `pass` 字段获得认可。
- **生成成功不等于质量合格**：审核者读取最终图及关键证据。中文标签、箭头、对照/证据强度、邮件尺度可读性分别检查；不拿分辨率、OCR 总分或 provider 名字替代。
- **原图通过不等于发送图通过**：压缩、叠字、格式转换可能引入问题，最终审核绑定实际 CID 资产字节；优先修派生步骤，避免无谓重画。
- **声明模型与实际模型分离**：网关缺失 returned model/request ID 如实记录，可信 runner 能证明请求关联，但无法证明第三方后台权重，也不宣称防管理员篡改。
- **外部补图不封死**：可移植导入仍可用；可验证程度不足时经人工核验使用，保留 `self_reported`，不捏造成 `runner_verified` 或免审。

### 9.5 第三轮：约束、预算与失败率

- Handoff 由 24 个重叠字段收敛为主体、核心判断、机制、证据、范围、标签六部分；证据关联/版本/hash 放附属元数据，风格只编译一次。精简表达不等于降低信息密度或删掉关键关系。
- 取消“有中文就必须混合”“固定标签数/结果数”“各种主题色禁止项”作为机械路由或否决条件。用户认可的原生图仍可用；确有文字问题时再定向修复或混合派生。
- 草稿审稿用独立上下文，可与编辑用同一已批准模型；不要求购买新模型或多模型投票。图审能力必须实际支持图输入，不把文本审核伪装成图审。
- 单期最多两轮定向修订复核，图片最多一次质量修复并计入总生成上限；所有层共用调用预算。不会每层重试 3 次叠成几十次调用。
- 审核不可用保留待审预览，人可明确替代；不等同质量不合格，不无限卡住制作。自动模式下仍不免除必须的审稿。
- 图片服务全部不可用可走无图深度；质量失败撤图则待人工确认。曾经失败的服务不能永久熔断，默认主备范围必须在运行前冻结，不临时外发给未知网关。
- 复用未变卡片及材料，只重新核验依赖变化的摘要/handoff/图片；不可用旧审核记录批准新内容。优先检查低成本确定性错误，减少高成本无效绘图。

### 9.6 第四轮：跨章节一致性与验收

回查第 2/4/6/8/9/10/11/14/15/17/18/19 节：

1. 所有“研究存在即要求图片”的现行条款都改为“选用图片才需要资产门”；无图版不要求伪造图片审核。
2. 深度名额与新闻数定义一致；工程内容提升深度后保留原轨道，不重复渲染，不自动用低质稿填补空位。
3. AI 审稿和人工发布权限分离；技术缺图、质量撤图、审稿不可用和来源自报的自动模式边界分别列明。
4. 初审、返工、最后核验的结果绑定正确输入/最终资产，不能用源图通过掩盖压缩后损坏。
5. 路由、调用、图片批准与实际发送绑定同一套记录，兼容历史不意味着豁免新候选；未验证模型名不导致虚假的确定性。

### 9.7 建议优先级与明确不做的事

第一批优先落地：统一版本与发布入口 → 独立审稿只报告建议 → 六字段 handoff 编译与受控调用记录 → 无图深度/最终图片审核的端到端影子测试。实际门禁应与记录生成一起迁移，不能只先加一个严格 verifier 让旧制作流程全被拦住。随后再启用自动定向返工和切换生产，顺序以主需求 19 节为准。

明确不做：不新建通用多智能体平台、不采用无限“审稿—重做”循环、不用更多否定 Prompt 修复架构缺口、不强制每天研究/图解配额、不把六字段扩成几十个必填细项、不默认引入新模型供应商、不在本轮直接部署。
